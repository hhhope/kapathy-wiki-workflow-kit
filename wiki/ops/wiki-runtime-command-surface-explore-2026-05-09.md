# Wiki Runtime Command Surface Explore

## Trigger

The user asked why the repo wiki seemed to contain many commands or runtime
capabilities, while the first command implementation exposed only
`/wiki:status`.

## Clarification

The first implementation treated the immediate pain as a missing status entry:
refresh the manifest, show pending inbox files, and expose the generated status
surface through a repo-local Codex command.

That solved a narrow visibility problem, but it did not expose the broader
runtime chain already recorded in wiki/spec pages.

## Current Alignment

The wiki runtime command surface should distinguish:

- committed command entrypoints under `commands/`
- existing runtime scripts under `scripts/`
- stable wiki/spec contracts under `wiki/ops`, `wiki/adr`, and `openspec/specs`

The current command surface maps existing runtime layers into `/wiki:*`
commands without adding new query engine, graph UI, score formulas, or change
queue automation.

## Command Meaning

| Command | Meaning |
|---|---|
| `/wiki:status` | Refresh and summarize wiki status and pending inbox visibility. |
| `/wiki:manifest` | Inspect the machine-readable manifest generated by status. |
| `/wiki:inbox` | Review pending inbox material and optional intake draft route. |
| `/wiki:graph` | Run structural graph extraction and relation analysis. |
| `/wiki:scorecard` | Run semantic scoring and utilization banding. |
| `/wiki:route` | Generate source-integrated runtime reading order. |
| `/wiki:context` | Build runtime context and bounded context injection. |
| `/wiki:apply` | Summarize bounded self-directed execution guidance without executing it. |

## Why The First Pass Missed The Larger Surface

The first pass optimized for the confirmed status gap and command packaging
correction. It also preserved the boundary that status must not become query,
scorecard, graph UI, or change queue.

The missing step was not runtime capability creation; those capabilities already
existed. The missing step was product-surface mapping: turning the existing
runtime layers into visible repo-level `/wiki:*` entrypoints.

## Boundary

This trace is exploratory context. It does not authorize new implementation
beyond the active OpenSpec change that owns the command surface.

## Runtime Correction

Later runtime evidence showed that the command-surface assumption was wrong for
current Codex CLI behavior:

- `codex-cli 0.130.0` discovers repo-local skills and exposes them as
  `$report-wiki-portfolio:<skill-name>` skill triggers.
- Installing the repo-local plugin makes the plugin visible and enabled, but it
  does not cause `plugins/report-wiki-portfolio/commands/*.md` to appear in the
  TUI slash menu.
- Files under `~/.codex/prompts/*.md` also do not appear in the current TUI
  slash menu. This explains why existing `/opsx:*` prompts are absent alongside
  the attempted `/wiki:*` prompts.
- Official current CLI slash documentation lists built-in slash commands only.
  A public OpenAI Codex issue reports `~/.codex/prompts` no longer appearing
  after `codex-cli 0.117.0`, and that issue is closed as not planned.

The practical correction is that `/wiki:*` cannot currently be treated as a
supported repo-local Codex CLI delivery surface. The supported local surfaces
available in this repo are repo skills, plugin installation state, scripts, and
documented manual command bodies.
