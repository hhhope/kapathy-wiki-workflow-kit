# 涅槃项目一期交付看板

## 一、看板口径

- 一期定的范围就是当前承诺排期范围
- 当前不再讨论“一期要不要做”，而是管理一期内部功能颗粒度与技术承接颗粒度
- 看板只分三层：
  - `本期可承诺`
  - `内部推进中`
  - `待产品技术确认`

## 二、项目首页判断

| 维度 | 当前判断 |
| --- | --- |
| 对客主线 | 协议支付主链路、网关、账户基础能力是当前最接近可承诺的部分 |
| 内部主线 | 退款、BM、绑卡、查询、补单补发清算仍在推进，不能整体视为已交付 |
| 关键 gap | 一期范围虽然确定，但一期内部很多功能仍只有部分技术承接 |
| 最易错位区域 | 分账耦合、退款治理、BM 运营能力、AD/配置迁移 |

## 三、一期时间与里程碑看板

| 节点 | 日期 | 当前判断 |
| --- | --- | --- |
| M2 基础协议支付 | 2026-07-23 | 一期最终承诺节点 |
| 统一网关 | 2026-06-30 | 受 NACOS 回归影响 |
| 计费模型搭建 | 2026-06-23 | 与失败计费、退款手续费等能力存在耦合 |

| 协议支付退款完成窗 | 2026-07-10 | 距 M2 仅剩较小缓冲 |

## 四、一期 gap 与风险

| 维度 | 当前 gap / 风险 |
| --- | --- |
| 功能 gap | 一期需求里 BM、退款治理、绑卡后段、失败计费等颗粒度高于当前稳定技术承接颗粒度 |
| 时间 gap | 绑卡、退款等后段能力集中压在 2026-05 到 2026-07，缓冲较小 |
| 资源 gap | 主链路、分账、网关、迁移项共用关键人，新增需求不是加在空闲带宽上 |
| 管理风险 | 产品按需求包看范围，技术按模块拆单推进，容易造成对客口径和交付口径错位 |

## 五、本期可承诺

| 模块 | 当前口径 | 备注 |
| --- | --- | --- |
| 协议支付主链路 | 一步支付作为一期主链路能力，可作为已明确承接项持续推进 | 仍需统一“开发完成/测试通过/可交付”口径 |
| 支付结果通知 | 已有明确承接，可视为主链路组成部分 | 需补商户验收口径 |
| 网关基础能力 | 已进入测试和回归阶段 | NACOS 接入后仍要回归，不宜过度承诺“完全闭环” |
| 账户基础能力 | 待分账户、分账接收户、统一动账等基础能力已有承接 | 更适合作为内部支撑能力表达，不单独对客包装 |

## 六、内部推进中

| 模块 | 当前口径 | 当前 gap |
| --- | --- | --- |
| 预支付 / 确认支付 | 已有排期，但不宜直接按完成能力对外表达 | 颗粒度和验收口径未统一 |
| 补单 / 补发清算 | 已进入推进范围 | 周报显示资源受挤压，节奏不稳 |
| 支付订单查询 | 有排期 | 查询字段是否满足对客场景仍待确认 |
| 绑卡 / 一键绑卡 / 解绑 / 绑卡查询 | 已进入一期功能清单，但整体仍在后排推进 | 技术承接不完整 |
| API 退款 | 已有技术承接 | 仅能说明基础能力推进中，不能等价为完整退款包 |
| 运营查询 / 详情 | 有排期 | 与 BM 完整能力仍有差距 |
| 配置迁移 / AD 迁移 | 技术有承接 | 持续被主链路挤压 |

## 七、待产品技术确认

| 模块 | 当前问题 | 管理动作 |
| --- | --- | --- |
| BM 对账 / 回单 / 退款入口 | 产品需求明确，但技术没有完整成包承接 | 先明确一期交付颗粒度 |
| 退款审核 / 批量退款 / 手续费展示 | 已进入需求，但未形成稳定排期承接 | 先明确是否属于一期必交功能 |
| 协议支付用于分账 | 一期内是否作为必须闭环能力仍不清楚 | 必须单独拉齐边界 |
| 分账校验接口 / 分账计费归属 / 兼容老配置 | 讨论结论较多，但仍缺稳定实现边界 | 产品技术共同冻结 |
| 分账退款 | 仍待重新评审 | 评审完再更新排期与承诺 |
| 失败计费 | 需求已提出，但承接边界不清 | 明确 owner 和系统归属 |
| 异步通知参数整理 | 是补字段还是做统一改造仍不清 | 明确工作量级别 |
| 新代收 / 签约支付 / 路由重发 | 是一期兼容能力还是后续预留能力 | 先定归属，再定承诺 |

## 八、调配建议

| 调配方向 | 建议动作 |
| --- | --- |
| 主链路保护 | 把补单、补发清算、查询、通知收口明确成一期主链路收尾包，不再与外围需求混排 |
| BM 分包 | BM 查询、对账、回单、退款入口独立管理，避免影响主链路口径 |
| 退款分层 | API 退款与 BM 退款治理分层管理，先保基础退款，再扩运营治理 |
| 分账隔离 | 协议支付用于分账、分账退款、分账计费归属单独拉齐，不直接吞主链路资源 |
| 测试倾斜 | 2026-04 到 2026-07 优先保证协议支付主链路与退款主链路回归窗口 |

## 九、管理动作

### 1. 每周固定更新

- 更新“一期可承诺”区是否有新增项
- 更新“内部推进中”区哪些项已经进入联调 / 测试 / 可交付
- 更新“待产品技术确认”区哪些项已冻结结论

### 2. 对客口径使用方式

- 对客只从“本期可承诺”区取口径
- “内部推进中”只能作为内部状态同步，不直接承诺为交付完成
- “待产品技术确认”不得进入正式对客承诺

### 3. 对内管理使用方式

- 产品看功能颗粒度是否完整
- 技术看承接颗粒度是否完整
- 项目管理看哪些项已具备对客条件，哪些项只是内部推进状态

## 十、一句话管理结论

一期范围本身已经确定，当前真正要管理的不是“做不做”，而是：

- 一期功能里哪些已经可以稳定承诺
- 哪些还只是技术推进状态
- 哪些仍缺产品技术共同确认

只有把这三层分开，对客口径和实际交付才不会继续错位。
