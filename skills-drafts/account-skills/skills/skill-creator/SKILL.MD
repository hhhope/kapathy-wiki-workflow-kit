# Skill Creator

把重复流程和防错规则固化为 AI 可执行的结构化文档。

---

## ⚠️ 禁止行为（任务开始前扫一遍）

- ❌ 在没有理解触发场景之前就开始写 SKILL.md
- ❌ 把操作细节写进 description（description 只写触发条件）
- ❌ 用描述式语言写规则（"注意并发安全"）而不是规则式（"禁止不加锁直接写"）
- ❌ 创建 Skill 后不验证触发词是否准确
- ❌ 把所有内容塞进 SKILL.md body，不使用 references/ 分层

---

## 意图路由

| 用户意图                    | 执行阶段              |
|---------------------------|---------------------|
| 从零创建 Skill              | Phase 1 → 2 → 3 → 4 |
| 已有草稿，要优化             | Phase 3 → 4         |
| Skill 触发不准              | Phase 4（触发优化）   |
| 检查现有 Skill 质量          | Phase 5（质量诊断）   |
| 把对话流程固化为 Skill       | Phase 1（意图提取）   |

---

## Phase 1 — 意图提取

**如果当前对话已有工作流程**（用户说"把这个变成 skill"）：

```
从对话历史中提取：
  - 用了哪些工具 / 命令
  - 执行顺序是什么
  - 用户做了哪些纠正（这是禁止行为的来源）
  - 输入/输出格式
→ 向用户确认提取结果，补充空白项
→ 进入 Phase 2
```

**如果是全新需求**：

依次确认以下四项，一次问完，不要分多轮：

```
1. 这个 Skill 要让 AI 做什么？（核心能力）
2. 什么情况下触发？（触发词、场景、平台）
3. 期望输出是什么格式？（文件 / 命令 / 文本 / 代码）
4. 有没有 AI 经常犯的错误要防范？（禁止行为的来源）
```

---

## Phase 2 — 深度访谈

在写任何文档之前，主动追问：

```
边界情况：
  - 什么情况下不应该用这个 Skill？
  - 和哪些现有 Skill 有重叠？怎么区分？

依赖项：
  - 执行前需要读哪些文件 / 配置？
  - 依赖哪些外部工具或权限？

错误来源：
  - AI 在这个领域最常犯什么错？
  - 有没有代价特别高的操作（不可逆、影响生产）？

成功标准：
  - 怎么判断 Skill 执行得好不好？
  - 有没有可以量化的验证点？
```

访谈完成后，**列出所有确认项，等用户确认再进入 Phase 3**。

---

## Phase 3 — 起草 SKILL.md

按以下结构生成，每个区块有约束：

### frontmatter（触发层）

```yaml
---
name: {skill-name}           # 小写连字符，≤20字符
description: "{触发条件描述}  # 只写条件，不写操作细节
                              # 包含正向触发词 + 隐含场景 + 必要的排除条件
                              # 适当'强推'：加'必须使用''即使没有明确说...也应触发'"
---
```

### body 结构（执行层）

```markdown
## ⚠️ 禁止行为（任务开始前扫一遍）
约束：
  - ≤5条，超过 5 条说明没有做优先级排序
  - 只列最容易触发且代价最高的
  - 规则式语言：❌ 禁止...
  - 末尾写"完整规则见底部"

---

## 意图路由（可选，规则 >10 条时必须加）
约束：
  - 表格格式：任务类型信号词 → 优先检查的规则/文件
  - 信号词来自用户真实输入语言，不是技术术语
  - 无匹配时的降级策略必须写清楚

---

## 前置条件（可选）
约束：
  - 只写执行前必须满足的条件
  - 每条能被明确验证（"X 文件存在" 而非 "环境准备好"）

---

## 核心规则
约束：
  - 规则式语言：禁止/必须/先…再…
  - 每条规则有对应的错误来源（至少心里清楚）
  - 不超过 15 条，超过则考虑拆分 Skill 或移入 references/

---

## 意图 → 命令索引（工具类 Skill 必须有）
约束：
  - 表格格式：意图 → 推荐命令 → 备注
  - 意图用自然语言，不用技术术语
  - references 文件在这里指定加载时机

---

## 常见错误速查（有明确错误码/错误信息时加）
约束：
  - 格式：错误信息 → 根因 → 解决方案
  - 不写泛化建议，只写具体的根因和解决步骤

---

## 完整规则参考（底部）
约束：
  - 顶部禁止行为的完整版本
  - 所有约束的详细说明
  - 这里是"查阅"区，不是"执行前读"区
```

### references/ 结构

```
references/
├── {command-a}.md      # 单个命令的详细文档
├── {schema}.md         # 数据结构定义
└── {examples}.md       # 完整示例（带注释）
```

references/ 文件规则：
- 超过 300 行必须加目录
- SKILL.md 里必须有明确的"先读 X 再执行 Y"绑定
- 按操作类型命名，不按字母顺序

---

## Phase 4 — 触发优化

**验证触发词：**

准备 5-10 个测试场景，每个场景写出用户实际会说的句子：

```
✅ 应该触发的场景：
  - "帮我在飞书 Base 里建一个项目追踪表"
  - "这个多维表格的公式怎么写"
  
❌ 不应该触发的场景：
  - "帮我看一下这个飞书文档"（这是 docs，不是 base）
  - "飞书日历怎么设置"
```

检查 description 是否能正确区分这两类场景，不能 → 修改 description。

**常见触发问题：**

| 问题 | 症状 | 修复方向 |
|------|------|---------|
| undertrigger | 该用时没触发 | description 加"即使...也应触发" |
| overtrigger | 不该用时触发了 | description 加明确的排除条件 |
| 触发词太技术化 | 用户用日常语言但没匹配到 | 在 description 里补充日常语言的同义词 |

---

## Phase 5 — 质量诊断

对现有 Skill 做质量检查，输出诊断报告：

```
1. description 检查
   - 有没有把操作细节写进 description？
   - 触发条件是否清晰？有没有边界排除？
   - 有没有 undertrigger 风险？

2. 结构检查
   - 禁止行为在顶部还是底部？
   - 有没有意图路由（规则 >10 条时必须有）？
   - references/ 有没有明确的加载绑定？

3. 语言检查
   - 规则是规则式还是描述式？
   - 每条规则能否追溯到具体失败来源？

4. 规模检查
   - SKILL.md body 是否超过 500 行？
   - 超过是否有 references/ 分层？

输出格式：
  问题项：[位置] [问题描述] [严重程度: 高/中/低]
  修复建议：[具体改法]
  优先修复：[最高代价的 1-2 个问题]
```

---

## 输出规范

**Claude 只输出草稿，不直接写入文件。**

每次输出之后：
- 说明每个设计决策的原因（尤其是禁止行为的来源）
- 主动指出哪些地方不确定，需要用户补充
- 等用户确认后再提交最终版本

---

## 完整规则参考

- ❌ 跳过 Phase 1/2，直接写 SKILL.md
- ❌ description 超过 150 词（越长越难精准触发）
- ❌ SKILL.md body 超过 500 行（需要拆分或移入 references）
- ❌ 规则区块使用描述式语言
- ❌ references/ 文件在 SKILL.md 里没有明确的加载触发点
- ❌ 禁止行为超过 5 条（说明没有做优先级判断）
- ❌ 直接写入用户文件系统（输出草稿，人来写）
- ❌ 在没有确认边界的情况下和现有 Skill 产生重叠
