# 分歧管理方法

这页定义什么情况下，agent 不应急着把分歧压成结论、规则或治理解释，而应先把分歧当成目标校准材料来保留。

## 核心判断

当用户和 agent 反复争论，不是在补事实，而是在不断校准“真正该保护的目标”时，当前对象就不再只是一个待回答的问题。

这时默认动作不是：

- 先写一个更干净的总结
- 先判断该不该进 `ADR`
- 先把它翻成 `spec / skill / wiki routing` 问题

而是先保留这轮分歧本身，尤其是它怎样从表面对象逐步重定向到更深目标。

## 最小原始材料包

在总结、命名或晋升之前，至少要先保留下面这些材料：

- `rejected_framing`
  - 当前被持续否掉的 framing、对象或总结是什么
- `correction_pressure`
  - 用户反复施加的纠偏压力是什么
- `redirection_moment`
  - 什么时候开始发现“争的不是这个”
- `clarity_state`
  - 当前更诚实的状态是什么
- `protected_target`
  - 如果已经看得见，这轮分歧在保护什么更深目标；看不见就明确保留没看清

这是一条反压缩边界。

如果这组材料还没保住，后面的总结都不可信。

## 反压缩状态

这套方法必须显式保留两种 `not yet` 状态：

- `I haven't seen it clearly yet`
  - 表面对象已经错了，但更深目标还没看清
- `We should not name the pattern yet`
  - 当前还主要是纠偏压力，没到能命名判断方式的时候

没有这两层，系统会过早奖励抽象，把活的分歧重新压扁。

## 第一次正向命名门槛

第一次把分歧正向命名成某种“判断方式”时，门槛要高。

不是因为：

- 聊天看起来平静了
- 现在能写出一个漂亮总结了
- 用户暂时没继续反对

而是只有同时满足下面 3 条，才允许第一次正向命名：

1. 被否掉的对象已经稳定
2. 已经发生了重定向，能明确看见“争的不是这个”
3. 这个名字能解释分歧是怎么变化的，而不只是解释最后的结果

一句话：

`只有当命名能解释分歧的运动，而不只是总结结果时，它才算有效。`

## 方法服从材料

这套方法是镜子，不是过滤器。

所以：

- 原始分歧材料优先于方法语言
- 如果框架和分歧冲突，保留分歧，削弱框架
- 不允许为了满足方法结构去重塑 live disagreement

真正的顺序应该是：

1. 先保过程
2. 再提炼判断方式
3. 再决定是否晋升为 `retro / ADR / spec / skill`

## 下游边界

这套方法不是下游容器本身，而是这些容器之前的上游层。

默认边界：

- `wiki/ops retro`
  - 分歧已经足够成形，需要 repo-visible 保留其校准作用
- `ADR`
  - 分歧已经完成足够多的校准工作，并形成跨 change 稳定决策
- OpenSpec spec
  - 分歧已经稳定到足以 formalize 成 repo-default workflow requirement
- repo-local skill
  - 分歧已经稳定到可以变成可执行的行为路由

不应该直接从 live disagreement 跳到这些层，而跳过方法层。

## Runtime 路由

这套方法在运行时的默认接线很窄，只处理两个关键边界。

### 什么时候默认进入 `wiki/ops retro`

当下面这些条件同时出现时，默认应把分歧落成一条 `wiki/ops retro`：

- 分歧已经明显在做目标校准，而不是普通问答
- 最小原始材料包已经能保住
- 这轮分歧已经足够成形，继续只留在 chat 会丢过程
- 但它还没稳定到足以直接晋升成 `ADR`、spec 或 skill

换句话说：

`有 repo-visible 保留价值，但还没有 stable-decision 资格时，默认进 retro。`

### 不该直接进 `retro` 的情况

- 还只是零散纠偏，连最小材料包都保不住
- 已经形成稳定跨 change 决策，应该直接补 `ADR`
- 已经只是某条当前 change 的 closing judgment，应该写进 `archive-review.md`

### 最小 retro 形状

进入 `wiki/ops retro` 时，至少保留：

- 当前表层对象是什么
- 哪个 framing 被持续拒绝
- 分歧何时发生重定向
- 当前是 `not yet` 还是已到第一次正向命名
- 如果看得见，这轮分歧在保护什么目标

## 非目标

第一版不做这些事：

- 不把每次争论都自动升级成 `ADR`
- 不直接定义 runtime automation trigger
- 不证明 rollout 已经完成
- 不用一套固定模板替代真实分歧材料

## 一句话判断

`当分歧正在校准目标时，先保住分歧怎样变化，再决定它该变成什么结论。`
