AI Agent 时代产研协作观察报

262 条来源记录之后，行业真正争论的不是工具，而是谁定义目标、谁承担判断、谁审查结果、谁拥有作业系统。

头版判断

产研协作正在从人力流水线，变成人机作业系统。

Agent 不是把工程师变快的插件。它把 ticket、spec、PR、CI、eval、wiki 变成可执行对象。人不再只负责把上下文传给下一个人，而要负责目标、边界、判断和后果。

旧问题：怎么让人更快交付？

产品、设计、工程、测试按顺序接力。上下文靠会议和文档搬运，质量靠末端验收兜底。

新问题：怎么让系统可执行、可审查、可沉淀？

人定义目标和判断边界，Agent 执行和自证，结果进入 PR、review packet、eval、wiki、rules。

五张图读懂主线

主线图与证据边界

主线只有一句：Agent 的核心价值不是替人做判断，而是把原来靠人转述、追踪、补文档、补测试的中间执行工作，变成可执行、可审查、可回放、可沉淀的系统循环。

  • 01 争议行业表面争“代码会不会被解决、PM 会不会消失、小团队会不会替代大组织”。落到公司内部，真正争的是目标、上下文、执行和责任怎么重新分工。
  • 02 结构公司内部协作更像一只哑铃：一端是人的判断端，一端是系统执行端，中间靠 spec、eval、review packet、wiki、rules、issue、PR 连接。
  • 03 本质不是中间层消失，而是转述型中间劳动被压缩，判断型中间责任被抬高。执行可以系统化，判断必须更清楚。
  • 04 循环Agent 输出不能只停在答案。它必须进入 review packet、eval、CI、wiki、rules 和 owner 判断，才算进入公司的作业系统。
  • 05 动作读者不要先买工具。先选一个高频、可验证、风险可控的工作流，跑 30-60 天试点，观察目标清晰度、返工、审查、失败写回和责任归属。

行业在争什么

证据能支撑什么，不能支撑什么

表面上，行业在争“Agent 会不会写完代码、PM 会不会消失、公司会不会变成极小团队”。但把 2026 年 1 月到 5 月 11 日的公开信源放在一起看，真正的争点不是职业消失，而是公司能不能把工作交给 Agent，又能不能把结果审回来。

这篇草稿的数据底座

  • 截至 2026-05-11，本地源池包括 43 条精选来源图谱、88 条扩展线索、95 条公开时间线条目、36 条播客 / 视频讨论线索。
  • 这不是“全网统计”，也不是 262 篇全部深读后的结论；它能支撑的是公开讨论方向、信源分布和可复核的章节假设。
  • 微信文章、二手媒体和播客摘要只作为线索路由；关键判断优先回到公司原文、工程博客、研究报告和上游访谈。

共识一：工作入口正在从聊天框，回到真实工作对象

OpenAI Symphony 把 issue tracker / Linear 当作 coding agent 的控制面；GitHub Copilot coding agent 把任务挂在 GitHub issue、branch、PR、Actions 和 repo policy 上；Atlassian Rovo in Jira 把 backlog、plan、code、PR 连起来；Google Jules 强调异步、仓库集成、计划、diff、测试和 GitHub 集成。它们各自卖的产品不同，但共同方向很清楚：Agent 不是孤立聊天窗口，而是进入 ticket、issue、PR、workflow、CI 这些已有作业对象。

共识二：执行变快以后，治理、验证和责任反而更重

Stack Overflow 2025 Developer Survey、Google DORA 2025、GitLab DevSecOps、Thoughtworks 的 AI-first software engineering 讨论，都在提醒同一件事：AI 采用率和代码产出提高，并不自动等于交付质量提高。信任、调试、稳定性、平台治理、合规、review、测试和回滚仍然是瓶颈。Replit 数据库事故类案例则是反例边界：没有权限、隔离、审查和回滚，自动化只会放大事故半径。

共识三：人的责任没有消失，而是上移

Karpathy 把专业 AI coding 和“vibe coding”区分开，核心不是模型能不能写，而是人是否仍然理解系统、上下文、质量和风险。Addy Osmani 把 coding agents 明确拉回“管理多个 agent”的能力：清晰目标、分派任务、验证结果、异步沟通。Keith Rabois 的 barrels / ammunition 框架和 Cat Wu 关于产品判断、角色边界变薄的讨论，也都指向同一个组织问题：真正稀缺的是能把目标、判断、执行和结果串起来的人。

  • 争点不是“Agent 是否聪明”，而是它能否进入真实工作对象，并被公司治理、验证、审查、追责。
  • 共识执行层会被系统化；目标、边界、验收、风险承受和 owner（责任人）不能被系统吞掉。
  • 分歧供应商会强调替代和效率，研究报告和事故案例提醒：如果作业系统不变，效率提升可能转化成返工、失控和信任下降。

公司内部协作正在变成一只哑铃

候选观察框架，不是行业标准术语

“哑铃”不是行业术语，是我们对公开信源的一个观察框架：左端是人的判断、目标和责任，右端是系统化执行、验证和回放，中间那根杆是 spec、eval、review packet、wiki、rules、issue 和 PR。

过去的产研协作像一条人力交接链：PM 解释需求，设计补体验，工程拆实现，QA 兜质量，管理者靠会、表格和 Jira 追进度。这个系统能跑，但它把很多关键上下文藏在人脑里。每次交接都会丢信息，责任也容易在“我已经同步过了”里变模糊。

Agent 进入以后，变化不是“中间人消失”。更准确的说法是：转述型中间劳动被压缩，判断型中间责任被抬高。找资料、拆任务、生成初稿、补测试、整理证据、更新文档，这些中间执行工作开始被做成可排队、可审查、可复用的系统单元；但目标、非目标、用户取舍、风险承受、验收标准、发布判断，仍然必须由人承担。

为什么说两端都会变重

执行端变重，是因为 OpenAI Harness、Block AI-Assisted Development、JetBrains Central、Sourcegraph、GitHub Copilot coding agent 等材料都在强调同一类基础设施：repo knowledge、skills、tests、CI、sandbox、credentials、audit、branch protection、cost attribution、observability。没有这些，Agent 只是更快地制造不可控产物。

判断端变重，是因为 Amazon、Shopify、Duolingo、Coinbase、Microsoft Frontier Firm、McKinsey Agentic Organization 这些组织讨论都在把 AI 从“个人效率工具”推向“组织作业方式”。一旦执行可以外包给系统，公司反而更需要清楚说明：谁是 owner（责任人），什么不能做，什么结果才算过关，失败以后由谁收拾和写回。

  • 左端目标、用户、边界、风险、验收、发布判断。这些不能交给 Agent 自己决定。
  • 右端检索、拆解、生成、实现、验证、证据整理、知识写回。这些开始变成系统执行能力。
  • 中杆spec、eval、review packet、wiki、rules、issue、PR。它们把人的判断翻译成可执行上下文，把系统输出翻译成可审查证据。

主要依据：OpenAI Harness Engineering / Symphony；GitHub Copilot coding agent；Atlassian Rovo/Jira；Google Jules；JetBrains Central；Block AI-Assisted Development；Sourcegraph AI agents；Microsoft Frontier Firm；McKinsey Agentic Organization；Deloitte 作业模型材料；Keith Rabois 的 barrels / ammunition 框架；Karpathy / Addy Osmani 关于 agentic engineering 与 Agent 管理的实践讨论。

证据边界

  • “哑铃”是本文候选观察，不是已被行业命名的标准模型。
  • 组织瘦身、AI-first 招聘、一人公司叙事不能直接等同于成熟 Agent 作业系统。
  • 中间层不是消失，而是被拆成两部分：可系统化的执行，以及必须更清楚归属的人类责任。

作业系统变了

从交接链到可审查作业循环

作业系统变了，意思不是换一个 AI 工具入口，而是公司把工作交出去、收回来、审清楚、再沉淀的方式变了。过去靠人传上下文；现在要把上下文做成 Agent 能执行、团队能审查、系统能写回的对象。

在旧协作里，需求、设计、工程、测试之间靠人解释。一个好的 PM 或 TL 往往承担大量隐性中间劳动：把业务目标翻译成工程任务，把工程约束翻译回业务语言，把风险翻译成排期和验收，把问题翻译成会议纪要和 Jira 状态。这个中间层一直存在，只是过去主要由人承担。

Agent 的变化，是把其中一部分中间执行劳动变成系统对象。ticket 可以带上下文，spec 可以定义目标和非目标，PR 可以承载 diff、测试、日志和风险说明，eval 可以把验收从主观感觉变成可重复检查，wiki / rules / skills 可以把失败和经验写回下次执行。OpenAI Harness 和 Symphony、GitHub issue-to-PR agent、Atlassian Rovo/Jira、Stripe payment integration eval、Block 的 AGENTS/HOWTOAI/skills，都在指向这个方向。

目标 / 非目标 -> spec / issue / 上下文 -> Agent 队列 -> diff / 草稿 / test / log -> review packet -> eval / CI / owner 判断 -> wiki / rules / test 写回

Agent 把中间执行层变成可审查循环

这句话要写实一点：Agent 没有创造一个新的管理层，也不能自己批准自己。它真正能改变的，是把过去散落在会议、私聊、文档、脚本和个人经验里的中间执行动作，组织成一个可审查循环。人给目标和边界，系统拿到可执行上下文，Agent 排队执行，输出带上依据、验证、失败项和待判断问题，最终由 owner（责任人）决定是否接受，并把失败写回系统。

OpenAI 的 Codex agent loop 把 user、model、tools、state、safety policy 明确成循环；Symphony 把 issue tracker 变成编排入口；Anthropic Managed Agents 强调长期任务需要持久会话、沙箱和凭证隔离；Block 的 testing pyramid、guardrails、skills 和 Actionable CI 则说明 Agent 工作不能只看生成结果，还要看验证、反馈和写回。

什么算“可审查”

  • 输入目标、非目标、样例、反例、权限边界、数据入口、测试方法、验收标准要写清楚。
  • 过程Agent 用了哪些上下文、调用了哪些工具、跑了哪些检查、跳过了什么，都要能被回放。
  • 输出不是只给答案，而是给变更点、依据、验证结果、失败项、风险和待 owner（责任人）判断的问题。
  • 写回失败要进入测试、rules、wiki、skill、review checklist，否则下一轮只是重复犯错。

所以这不是“全自动驾驶”。高风险节点仍然需要人审、可追责、可回滚。Agent 的价值不在于省掉判断，而在于让执行层变得更可见：哪里缺上下文、哪里没有测试、哪里 owner（责任人）没有说清楚、哪里系统没有留下证据，都会被更快暴露。

证据边界

  • 不能写“Agent 已接管完整 SDLC”。更准确的是：部分中间执行动作正在从人脑和会议迁移到可执行工作对象。
  • “review packet（审查证据包）”是本文用来概括输出证据包的表达，不是所有产品都采用的标准名词。
  • 工具页证明作业面方向，研究报告和事故案例提醒治理风险；两类证据要一起用，不能只拿供应商叙事写结论。

现有公司的人该怎么做

按角色调整作业方式
CEO / GM

别把 AI 当采购项目

  • 选一个真业务瓶颈做 30-60 天试点。
  • 明确质量、风险、成本和责任边界。
  • 用流程结果考核，不用“用了多少 AI”考核。
Product / PM

从需求转述者变成判断 owner（责任人）

  • 写清目标、非目标、用户场景和验收标准。
  • 把 ticket / spec / wiki 做成 Agent 可执行上下文。
  • 保留取舍权，不能把产品判断外包给模型。
Designer / Research

把体验判断变成可测试样本

  • 沉淀用户语境、反例、边界场景和体验红线。
  • 用原型和 review packet 审查 Agent 产物。
  • 把“像不像人话”变成示例和检查项。
Engineer / TL

从写代码扩展到管理执行系统

  • 设计工具权限、上下文入口、测试和回滚。
  • 审查 Agent 输出是否真的满足 spec。
  • 把失败写回 eval、lint、guardrail、skill。
QA / Data / Ops

把反复出错的地方变成 eval

  • 从末端兜底转向前置风险样本库。
  • 把缺陷、异常、客诉、合规点结构化。
  • 用可复跑检查证明 Agent 没有只会演示。
Manager / HR

重写岗位边界和成长路径

  • 区分可自动化执行和必须人类判断的工作。
  • 训练员工写上下文、审证据、管风险。
  • 调整绩效：看结果质量、系统沉淀和协作吞吐。

我们应该怎么做

本地作业原则

三条原则

  • 目标人定。业务目标、用户价值、优先级、风险承受度不能交给 Agent。
  • 过程可委托。检索、整理、生成、实现、验证、回放可以交给 Agent。
  • 结果可审计。所有输出必须进入 PR、review packet、eval、wiki、日志这类可追踪对象。

第一条试点链路

  • 从会议材料、文章或需求进入。
  • 沉淀成 spec / wiki / issue。
  • Agent 产出草稿、代码改动或 review packet。
  • 人审查判断，失败写回规则、测试、skill、wiki。
