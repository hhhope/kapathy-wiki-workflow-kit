# DDL Review Skill

对数据库建表语句做五层递进评审，输出结构化报告。

---

## ⚠️ 禁止行为（任务开始前扫一遍）

- ❌ 分多轮输出，每轮说一部分——必须一次性输出完整报告
- ❌ 只看单张表，不做跨表一致性检查
- ❌ 报告中只列问题不给修复建议
- ❌ 在没有拿到全部相关表 DDL 之前就做 BC 归属判断
- ❌ 把"字段名拼写风格不统一"和"索引引用不存在的列"列同等优先级

完整禁止行为见底部。

---

## 意图路由

| 用户信号 | 执行重点 |
|---------|---------|
| 单张表 DDL | Layer 1~3，跳过 Layer 4（跨表），执行 Layer 5 |
| 多张表 DDL（同一业务） | 全量五层，重点 Layer 4 跨表一致性 |
| 金融/支付/结算/账务领域 | 全量五层，Layer 5 DDD 必须包含聚合根、BC 边界、事件溯源三节 |
| 用户说"只看索引" | 只执行 Layer 1 + Layer 2 中索引相关项 |
| 用户说"只看字段" | 只执行 Layer 2 + Layer 3 |

---

## 五层评审框架

### Layer 1 — 硬错误（DDL 执行失败）

扫描会导致 DDL 执行报错的问题，必须第一个输出，标记 🔴：

```
检查项：
- 索引引用的列名是否存在于表定义中
- 外键引用的表和列是否存在
- 重复的列名或索引名
- 数据类型语法错误
- 主键定义冲突
```

### Layer 2 — 字段类型问题（运行时隐患）

标记 🟡：

```
检查项：
- 跨表 JOIN 字段类型是否一致（尤其是 id、member_id、account_id 等关联字段）
- tinyint(1) 被 JDBC 映射为 Boolean 的陷阱（有超过 2 个枚举值时不能用 tinyint(1)）
- update_time 是否有 ON UPDATE CURRENT_TIMESTAMP
- decimal 精度是否满足金融场景（金融金额建议 decimal(18,2) 或更高）
- varchar 长度是否合理（手机号用 varchar(20) 而不是 varchar(255)）
- timestamp vs datetime 选择（timestamp 有 2038 问题）
```

### Layer 3 — 逻辑/语义问题（对账和一致性风险）

标记 🟠：

```
检查项：
- 同一业务实体跨表的状态枚举是否统一（值和含义）
- 状态值是否连续，有无跳号
- 同一概念字段名是否一致（balance vs amount 代表同一语义时）
- version 初始值跨表是否统一（乐观锁语义）
- 批次表和明细表的金额字段是否有约束关系说明
- 软删标志位命名是否统一（deleted vs is_deleted vs del_flag）
```

### Layer 4 — 缺失字段（功能和审计盲区）

标记 🔵，分两档：

**必须有（生产环境缺失即为问题）：**

| 字段 | 场景 | 说明 |
|------|------|------|
| `deleted tinyint` | 所有业务表 | 结算/支付数据禁止物理删除 |
| `update_time ON UPDATE` | 所有业务表 | 不能只有 DEFAULT |
| `creator_id` | 有操作人概念的表 | 和 auditor_id 不同，记录创建人 |
| `business_no` / `biz_no` | 对外交互的流水表 | 幂等键，溯源依据 |

**金融领域额外必须有：**

| 字段 | 场景 |
|------|------|
| `total_count` + `success_count` + `fail_count` | 批次表，对账必须 |
| `fail_reason` / `error_code` | 有失败态的批次表 |
| `settle_type` | 结算方式（T+N / 实时 / 手动） |
| `tenant_id` / `app_id` | 多租户体系 |

**按需补充（根据业务场景判断）：**
- `remark` — 异常处理写入原因
- `currency` — 涉及多币种
- `channel` — 涉及多渠道

### Layer 5 — DDD 设计（领域模型结构性问题）

标记 🟣，只在多张业务表时执行，金融领域必须执行：

**5.1 值对象重复**

如果同一对（如 `account_id + account_id_type`）在多张表重复出现，说明值对象未封装。
→ 指出重复次数和改动代价。

**5.2 聚合根不变性约束缺失**

检查点：
- 批次表（聚合根）和明细表（聚合内实体）的金额汇总关系是否有约束
- 批次状态和明细状态的联动规则是否在领域层有保障
- 聚合根能否自我校验（sum 一致性）

**5.3 BC 边界**

如果多张表结构高度相似但字段有差异（如正向结算表和退款结算表）：
- 判断是同一 BC 还是不同 BC
- 同一 BC：为什么不用类型字段区分而建两套表？
- 不同 BC：两个 BC 之间的关联和防腐层在哪里？

**5.4 扩展字段污染核心模型**

识别只属于特定业务线的字段（如 `cbpay_flag`、`bzz_flag`）混在核心主表里的情况。
→ 说明主表膨胀风险，建议扩展表或值对象。

**5.5 状态机缺少事件溯源**

结算/支付等强审计域：
- state 字段只记录当前状态，状态变更历史是否缺失
- 是否需要 event 流水表

## 输出格式

```markdown
# DDL 评审报告

> 涉及表：[表名列表]

## 一、硬错误 🔴
（有则列，无则写"无"，不要省略此节）

## 二、字段类型问题 🟡

## 三、逻辑/语义问题 🟠

## 四、缺失字段 🔵
### 4.1 必须补充
### 4.2 建议补充

## 五、DDD 设计问题 🟣
（单表可省略，金融多表必须有）

## 六、问题汇总
| 级别 | 问题 | 数量 |
|------|------|------|
| 🔴 硬错误 | ... | N |
| 🟡 类型问题 | ... | N |
| 🟠 逻辑问题 | ... | N |
| 🔵 缺失字段 | ... | N |
| 🟣 DDD 设计 | ... | N |
```

**输出规则：**
- 每个问题必须包含：位置（表名.字段名）+ 问题描述 + 修复建议
- 汇总表放在最后，用数量让优先级直观
- 无问题的层级不省略，写"无"，避免遗漏误解

## 常见错误速查

| 错误现象 | 根因 | 解决方案 |
|---------|------|---------|
| `Unknown column 'X' in 'key definition'` | 索引引用了不存在的列名，通常是列重命名后索引没同步改 | 检查所有 KEY 定义，对照列名修正 |
| JOIN 后索引不走，全表扫描 | 关联列类型不同（int vs bigint）导致隐式转换 | 统一关联列类型 |
| Java 代码读到 cbpay_notify_state 只有 true/false | tinyint(1) 被 JDBC 映射为 Boolean | 改为 tinyint(4) |
| 记录更新后 update_time 没变 | 缺少 ON UPDATE CURRENT_TIMESTAMP | 补充 ON UPDATE |
| 批次金额和明细汇总对不上 | 无一致性约束，由应用层保证但没有校验 | 在聚合根写入时做 sum 校验，或数据库触发器 |

## 完整规则参考

- ❌ 分多轮输出——一次输出完整五层报告
- ❌ 只检查语法，不做跨表一致性分析
- ❌ 把所有问题列同等优先级，不分层级
- ❌ 金融领域表跳过 DDD 检查
- ❌ 问题描述没有修复建议
- ❌ 缺失字段只按通用模板列，不结合业务场景判断
- ❌ 在没有全部相关表时就判断 BC 归属（需说明"需要其他表 DDL 才能完整判断"）
- ❌ 对无硬错误的情况省略 Layer 1 章节（要写"无"）
