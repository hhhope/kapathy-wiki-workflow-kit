# 涅槃项目一期交付看板

## 一、口径

- 截至日期：`2026-04-15`
- 一期范围：按当前承诺排期理解，最终时间锚点是 `M2 基础协议支付 2026-07-23`
- 本页只回答五个问题：
  1. 一期承诺里有哪些功能
  2. 截至今天这些功能做到什么状态
  3. 原排期时间是什么
  4. 现在还能不能按原预期交付
  5. gap 在哪，怎么调

## 二、当前结论

### 1. 当前最大问题不是“没排期”，而是三种信息没拉平

- 需求功能颗粒度大于技术当前稳定承接颗粒度
- 技术排期有开始时间和测试时间，但很多功能没有对齐“当前真实状态”
- 周报状态、模块排期、需求文档之间存在口径差异，直接影响对客承诺

### 2. 截至 `2026-04-15` 的一句话判断

- 一期主链路还在可控区，但后段缓冲偏小
- 退款、BM、绑卡、分账耦合不是“补充项”，而是已经会影响一期收口的实质性 gap
- 如果现在不按时间线重排管理口径，后面会出现“计划还在，实际不可承诺”的情况

## 五、现在能判断出的 gap

### 1. 时间 gap

- `补发清算` 原计划在 `2026-04-15` 启动，但周报状态已经不支持按原节奏乐观判断
- `协议支付退款` 计划在 `2026-07-10` 测试完成，距离 `M2 2026-07-23` 只剩 `13` 天缓冲
- `绑卡能力包` 集中在 `2026-05` 到 `2026-06`，属于一期后段功能，后续再被挤压就会直接影响 M2 收口

### 2. 功能 gap

- 产品需求里明确有 `BM 对账/回单/退款入口/批量退款/退款审核/失败计费`，但当前技术承接没有以同颗粒度稳定落地
- 当前技术排期更接近“主链路 + 部分运营查询”，而不是“完整一期需求包”

### 3. 资源 gap

- 协议支付主链路、分账耦合、网关回归、配置迁移并不是不同资源池
- 当前材料反复体现的现实是：关键人和关键测试窗口是共享的，而不是并行空闲带宽

### 4. 口径 gap

- 周报里“一步支付 100%”和测试进度口径存在冲突
- 这意味着当前最先要管的不是文案，而是“到底以哪个状态作为对客口径”

## 六、风险判断

| 风险项 | 当前等级 | 原因 |
| --- | --- | --- |
| 主链路收口风险 | 高 | 补单、补发清算、查询等还在近端窗口集中推进 |
| 退款闭环风险 | 高 | 退款主链路离 M2 只剩 13 天缓冲，且产品范围大于技术承接 |
| BM 交付风险 | 高 | 对客敏感，但当前没有完整稳定承接包 |
| 分账耦合风险 | 高 | 分账会持续反向吃主链路资源和边界 |
| 网关回归风险 | 中到高 | `NACOS` 接入后仍需回归和重压测 |
| 配置迁移风险 | 中 | 不一定阻断主链路，但会影响运营闭环和客户体验 |

## 七、调配建议

| 调配方向 | 建议动作 | 目的 |
| --- | --- | --- |
| 主链路保护 | 把补单、补发清算、查询、通知明确成一期主链路收尾包，禁止再和外围新需求混排 | 先保 M2 主线 |
| 退款分层 | 把退款拆成“基础退款链路”和“BM/审核/批量退款治理”两层 | 避免退款一包全压到 M2 末端 |
| BM 分包 | 把 BM 查询、对账、回单、退款入口单独做运营包管理 | 避免主链路和运营能力口径混在一起 |
| 分账隔离 | 把“协议支付用于分账”“分账退款”“分账计费归属”单列为跨模块确认包 | 不让分账无限吞主链路资源 |
| 测试倾斜 | 从现在到 `2026-07-23` 优先保协议支付主链路和退款主链路的回归窗口 | 保护有限缓冲 |

## 八、对客口径

### 1. 现在能对客说的

- 协议支付主链路正在推进，支付核心链路已进入明确收口阶段
- 网关和账户基础能力已进入联调 / 回归阶段

### 2. 现在不能直接整体对客说“已承接完成”的

- 完整退款包
- 完整 BM 能力包
- 协议支付用于分账包
- 失败计费、批量退款、退款审核、回单下载这类运营治理项

## 九、当前一句话结论

截至 `2026-04-15`，我现在能判断的不是“能不能做”，而是：

- 一期主链路还能继续保，但后段缓冲已经不大
- 真正的 gap 在于后段能力包和运营能力包没有和时间线一起被写实管理
- 如果后续不按“当前状态 + 原排期 + 预期交付 + gap + 调配动作”继续维护，一期对客口径仍会继续失真
