## 1. 写作方法契约

### 1.1 目标不是讲 Stripe 传记

这场 80 人分享的目标不是：

> Stripe 很强，Stripe 做了很多产品，Stripe 现在也在做 AI。

目标是：

> 借 Stripe 这个案例，讲清楚 AI 时代支付和金融能力建设到底在变什么。

所以 Stripe 在这篇里不是主角本身，而是一个高质量观察样本。真正主角是：

> AI 时代，当 coding 成本越来越低，金融交易能力如何从“把功能写出来”转向“把复杂领域设计清楚”。

### 1.2 全篇主线

一句话主线：

> AI 时代，coding 成本会越来越低，真正稀缺的不是把一个支付功能写出来，而是把复杂金融交易设计成稳定、清晰、可组合的领域语言。Stripe 切入 AI 支付快，不是因为它临时追 AI 热点，而是因为它过去十几年一直在做支付行业最难但正确的事：把商户、价格、订单、订阅、分账、身份、权限、风控、资金、结算和争议，收敛成开发者和商户能理解、能接入、能授权、能组合的对象、接口和规则。

这句话要贯穿全文。每个章节都必须回到它。

不用 `控制平面` 或 `可信交易执行层` 做中心词。前者太像技术架构直译，后者仍然偏结果层，解释不了 Stripe 为什么能快。

本文的中心词改为：

> 金融交易设计语言。

它要表达的不是“多一个支付入口”或“多一个执行系统”，而是：

> 谁能把复杂金融事物定义清楚、边界划清楚、接口做清楚、权限放得足够大但又有规则约束，谁就能在 AI 让代码和对接成本下降后，更快把真实交易交给软件和 Agent 执行。

可以用一个类比解释：

> 像零售或供应链系统一样，速度不是来自“写下单代码”本身，而是来自商品、库存、价格、订单、履约、退款、权限这些对象是否被定义清楚。设计语言统一以后，对接才会快，接口才会稳定，使用者权限才敢放大，复杂性才会被平台吸收。

### 1.3 读者最后要带走什么

听众听完后，应该能带走三个判断：

1. **AI 支付的核心不是入口变化，而是金融交易设计语言的重构。**
   入口可以从网站、App、收银台变成对话、搜索、Agent 或自动化任务，但真正难的是把商户、订单、价格、授权、风控、结算和责任这些对象定义清楚。

2. **Stripe 的 AI 价值不是突然冒出来的 AI 功能，而是长期做难事形成的领域设计能力。**
   API-first、Connect、Billing、Radar、Tax、Identity、Issuing、Capital、stablecoin、wallet、agent commerce 背后是一条对象、接口、权限、风控和资金关系不断收敛的能力累积线。

3. **我们要学的不是 Stripe 的某个产品，而是金融系统的关系设计能力。**
   谁能做什么、用谁的钱、在什么规则内、出错谁负责、证据怎么留存，这些才是 AI 时代金融系统的长期门槛。

这篇文章采用四个方法模块：

| 方法模块 | 用在哪 | 作用 |

## 4. 第 1 章：入口只是烟雾弹

时间：5 分钟，2 屏

### 4.1 这一章先砍掉的误解

不要从“AI 会不会帮用户点付款按钮”开始。这个问题太像入口视角。

表面看，AI 支付像是在争夺新的入口；但入口只是烟雾弹，真正的问题是支付公司凭什么继续获得服务溢价。

这一章先讲支付公司的底层商业问题：

> 支付公司凭什么收这个费率？

如果支付只被理解成扣款、收款、通道和结算周期，商户一定会比费率。支付公司要拿溢价，必须证明自己替商户减少了更多复杂性。

### 4.2 屏幕 1-1：费率背后买的是什么

商户表面上看到：

```text
费率 / 扣款 / 收款 / 通道 / 结算周期
```

商户真正愿意付费买的：

```text
更高转化
更少欺诈
更少拒付和争议
更低合规成本
更少对账成本
更简单订阅计费
更稳定平台分账
更快进入新交易场景
```

屏幕主句：

> 费率是价格标签，复杂性管理能力决定溢价权。

屏幕 1-1 话术：

> 我们今天先不急着讲 Stripe，也不急着讲 Agent 支付、stablecoin 这些新词。
>
> 先问一个更朴素的问题：支付公司凭什么收这个费率？
>
> 如果商户只看到扣款、收款、通道、结算周期，那支付一定会被放进费率表里比较。谁便宜、谁透明、谁成功率高、谁结算快。
>
> 但支付公司如果永远只是成本项，就很难拿溢价。它要回答的是：除了帮商户收钱，还帮商户少掉了什么麻烦？
>
> 能不能提高 checkout 转化？能不能减少欺诈和拒付？能不能处理争议？能不能支持订阅、税务、分账、对账和资金管理？
>
> 这些才是支付公司从通道走向基础设施的原因。

转场到屏幕 1-2：

> 那 AI 进来以后，为什么这个问题会变得更尖锐？因为很多基础能力会变便宜。

### 4.3 屏幕 1-2：AI 让什么变便宜，什么不会自动变清楚

AI 会让这些变便宜：

```text
写代码
接 API
搭页面
生成测试
搭 demo
试错流程
```

AI 不会自动理清：

```text
谁能交易
能买什么
谁授权
钱怎么走
什么要拦
出错谁负责
证据怎么留下
```

屏幕主句：

> AI 是成本下降的加速器，不是金融关系的自动设计师。

屏幕 1-2 话术：

> AI 会让写代码更便宜，接接口更快，做一个支付 demo 更容易。
>
> 这对支付公司是好事，也是压力。因为普通支付功能越容易被复制，越难靠“我也能收款”解释溢价。
>
> 但 AI 不会自动帮你把金融关系理清楚。
>
> 谁能交易？买什么？谁授权？钱怎么走？什么情况要拦？出了错谁负责？证据在哪里？
>
> 这些问题仍然要被设计。
>
> 所以这场分享不是从“谁多了一个付款入口”开始，而是从费率背后的溢价逻辑开始。

### 4.4 证据边界

- Stripe pricing：支付之外还呈现 Radar、Billing、Tax、Connect、Treasury、Issuing 等服务。
- Adyen pricing：Interchange++ 说明基础支付会进入成本透明和费率比较。
- PayPal fees：不同 checkout 服务对应不同费用和责任。

这些只证明“费率背后有服务差异”，不证明 Stripe 必胜。

### 4.5 1 -> 2 转场

> 如果接受这个判断，Stripe 就不是因为“也做 AI”才值得看。
>
> 它值得看，是因为它过去十五年的路径，一直在回答同一个商业问题：怎么让新业务用更低成本接入和管理更复杂的金融交易。
>
> 所以第二章我们不问 Stripe 是不是最强支付公司，而问：为什么 Stripe 会站在这场支付公司服务溢价竞争的中央？

## 5. 第 2 章：Stripe 站在战场中央

时间：6 分钟，2 屏

### 5.1 这一章先砍掉的误解

不能说：

```text
Stripe API 好，所以值得看。
Stripe 产品多，所以值得看。
Stripe 覆盖链路完整，所以站在中央。
```

这些都容易被反驳。PayPal 也有 API，Adyen 也能服务复杂企业支付，Visa/Mastercard 掌握网络规则。

本章真正要证明：

> Stripe 的样本价值，是它展示了支付公司如何把复杂金融场景变成低成本管理框架，并由此获得持续服务价值。

### 5.2 屏幕 2-1：不同支付公司的价值位置

```text
PayPal / 钱包路线
核心价值：消费者账户、买家信任、checkout 转化

Adyen / 企业收单路线
核心价值：全球收单、企业支付处理、成本透明、全渠道

Visa / Mastercard 路线
核心价值：网络规则、授权、token、清算、争议

Stripe 路线
核心价值：把新业务的金融复杂性做成可接入、可管理、可组合的产品语言
```

屏幕主句：

> 这些公司都强，但回答的问题不同。

屏幕 2-1 话术：

> 这里要先说清楚，我们不是说别的支付公司不重要。
>
> PayPal 很重要，它强在消费者账户、买家信任和 checkout 体验。
>
> Adyen 很重要，它强在全球收单、大型企业客户和全渠道支付处理。
>
> Visa、Mastercard 更不用说，它们掌握网络规则、授权、token、清算和争议体系。
>
> 这些公司都很强，但它们回答的问题不同。
>
> 今天我们的问题是：当支付接入成本越来越低，支付公司怎么继续证明自己的价值？从这个角度看，Stripe 是一个很好的样本。

转场到屏幕 2-2：

> 因为 Stripe 的路径，不是只做一个更便宜的 checkout，而是持续降低不同金融场景的管理成本。

### 5.3 屏幕 2-2：Stripe 降低的是哪几类管理成本

```text
开发者接入成本
API / docs / SDK / test mode / webhook

平台管理成本
Connect / onboarding / split payments / payouts

收入管理成本
Billing / Invoicing / Tax / Revenue Recognition / Metronome

风险管理成本
Radar / Identity / dispute / compliance

资金管理成本
Treasury / Issuing / Capital / Financial Connections

新交易接入成本
Agentic Commerce / machine payments / stablecoin / wallet
```

屏幕主句：

> Stripe 的产品扩张不是“产品多”，而是持续把不同金融场景的管理成本降下来。

屏幕 2-2 话术：

> Stripe 一开始降低的是开发者接入成本。API、文档、SDK、test mode、webhook，让开发者更容易把支付接进产品。
>
> 后来，它降低平台和 marketplace 的管理成本。Connect 解决的是平台、商户、买方、分账、入驻、结算之间的关系。
>
> 再后来，它降低 SaaS 和订阅业务的收入管理成本。Billing、Invoicing、Tax、Revenue Recognition，解决订阅、发票、税务、退款、收入确认这些问题。
>
> 再往后，它进入身份、风控、资金、发卡和信用。
>
> 所以 Stripe 一直在做一件事：把复杂金融场景变成更容易接入、更容易管理、更容易组合的产品语言。
>
> 这就是为什么 Stripe 会站在聚光灯下。不是因为它唯一会做支付，而是因为它的路径最适合说明支付公司如何从费率竞争走向服务溢价。

### 5.4 证据边界

- Stripe 2025 annual update 的 $1.9T 和 5M+ businesses：只证明样本规模足够。
- Connect：平台、多主体、入驻、分账、payout。
- Revenue Recognition：订阅、退款、争议、收入确认、audit-ready reporting。
- Agentic Commerce / machine payments / Bridge / Privy：说明进入新交易场景，不证明商业成功。

### 5.5 2 -> 3 转场

> 到这里，Stripe 的样本价值就清楚了：它不是只做收款，而是在不断降低复杂金融场景的管理成本。
>
> 但复杂性不能靠功能堆出来。
>
> 如果平台分账、订阅计费、税务、风控、资金、信用、自动化交易都堆在一起，而对象、边界、权限、规则、资金和责任没有被说清楚，系统只会越来越复杂。
>
> 所以第三章要讲真正的方法论：金融交易语言。

## 6. 第 3 章：真正的壁垒：谁来定义金融交易语言

时间：7 分钟，3 屏

### 6.1 这一章先砍掉的误解

AI 会让支付功能变便宜，但不代表支付能力变便宜。

一个支付按钮可以生成，一套金融交易语言不能自动生成。

本章判断句：

> 功能可以生成，关系必须设计。

### 6.2 屏幕 3-1：功能可以生成，关系必须设计

AI 能降低：

```text
写代码成本
接接口成本
搭页面成本
生成测试成本
试错成本
```

AI 不能自动定义：

```text
交易对象
授权边界
风险规则
资金路径
责任证据
```

屏幕 3-1 话术：

> AI 可以让支付功能更容易实现。它可以帮你写代码、接接口、搭页面、生成测试，甚至很快做出一个 demo。
>
> 但它不会自动帮你把金融关系理清楚。
>
> 这就是为什么我说，支付功能会变便宜，但金融关系不会自动变清楚。

转场到屏幕 3-2：

> 那金融关系到底要清楚到什么程度？至少要回答五个问题。

### 6.3 屏幕 3-2：金融交易语言五层图

```text
1. 意图
系统到底要完成什么交易？

2. 授权
谁允许它做，权限多大？

3. 规则
什么情况下能做，什么情况下必须拦？

4. 资金
钱从哪里来，到哪里去，怎么分、怎么结、怎么对？

5. 责任
出错谁负责，证据怎么留下？
```

每层缺失后果：

```text
意图不清：系统不知道自己到底在买什么
授权不清：自动化越强，风险越不可控
规则不清：只能停在低额度、强人工确认场景
资金不清：交易发起了，但金融结果不能闭环
责任不清：出错后只能说“模型做的”
```

屏幕 3-2 话术：

> 所谓金融交易语言，不是一个漂亮词。
>
> 它其实很朴素：就是把复杂金融场景说清楚，并且让它能被系统低成本管理。
>
> 这套语言至少有五层。
>
> 第一，意图。系统到底要完成什么交易？
>
> 第二，授权。谁允许它做？权限有多大？
>
> 第三，规则。什么情况下能做？什么情况下必须拦？
>
> 第四，资金。钱从哪里来？到哪里去？怎么分？怎么结？怎么对？
>
> 第五，责任。出错谁负责？证据怎么留下？
>
> 这五个问题回答不清楚，Agent、自动化、协议、钱包、稳定币都只能停在演示层。

转场到屏幕 3-3：

> 为什么这套语言会被付费？因为它不是概念，它直接降低商户管理复杂金融场景的成本。

### 6.4 屏幕 3-3：为什么这套语言会被付费

```text
意图
降低新场景理解和接入成本

授权
降低权限和凭据管理成本

规则
降低风险、欺诈、合规成本

资金
降低分账、结算、对账成本

责任
降低争议、审计、追溯成本
```

屏幕 3-3 话术：

> 比如平台分账，难点不是付款按钮，而是谁是平台、谁是商户、谁收钱、谁分账、谁退款、谁承担争议。
>
> 比如订阅计费，难点不是每月扣一次款，而是周期、用量、升级、降级、退款、发票、收入确认怎么处理。
>
> 比如 Agent 交易，难点也不是让 Agent 调一次支付 API，而是谁授权它、它能买什么、预算是多少、什么情况必须拦、出了错谁负责。
>
> 所以谁能用一套低成本框架，把复杂金融场景定义清楚、管理起来、跑起来，谁就有机会被持续付费。

### 6.5 证据边界

Stripe 证据只做 handle，不抢主线：

- 意图：Agentic Commerce、catalog、merchant tooling。
- 授权：Link wallets、Issuing、one-time cards、Identity。
- 规则：Radar、AI Security、token theft、tool misuse。
- 资金：Connect、Billing、Treasury、Bridge、stablecoin、MPP/x402。
- 责任：webhook、Dashboard logs、disputes、approval hooks、Revenue Recognition audit-ready reporting。

### 6.6 3 -> 4 转场

> 理解了这一点，我们再看 Stripe 的历史，就不会把它看成一串产品发布。
>
> 我们要看的是：它每一步到底降低了哪类复杂金融场景的管理成本。
>
> 第四章讲第一块阵地：开发者接口。因为只有先把支付接入变简单，后面平台、订阅、风控、资金和新交易场景才有可能继续接上。

### 6.7 方法论校验

这版没有扩散，前三章只完成 18 分钟内的三件事：

- 第 1 章：从费率进入，建立支付公司的商业本质。
- 第 2 章：从样本进入，解释为什么 Stripe 适合观察这个问题。
- 第 3 章：从方法进入，抽象出金融交易语言五层框架。

写法按既定格式：

```text
误解
-> 判断
-> 屏幕结构
-> 分屏话术
-> 证据边界
-> 转场
```

## 6. 第 4 章：Stripe 是怎么把这些能力攒出来的

### 6.1 章节任务

第 4 章用 Stripe 的公司路径证明第 3 章不是空想。

这一章不是普通时间线。它要证明：

> Stripe 今天讲 AI 支付，不是临时做了几个 AI 功能，而是过去十几年积累的支付、商户、风控、计费、资金和开发者能力，在 AI 场景下被重新调用。

### 6.2 开场句

可以这样开：

> 如果只看 2025、2026 年的 Agent commerce、stablecoin、wallet 和 machine payment，会觉得 Stripe 是突然追 AI 热点。
> 但把时间线拉回 2010 年，会发现它一直在做同一件事：把金融交易中的复杂动作拆成开发者和商户可以调用的对象。

### 6.3 不按年份流水账，按能力累积讲

第 4 章建议分成五个能力阶段：

```text
开发者接入能力
-> 平台和商户经营能力
-> 金融运营能力
-> AI 客户压力下的收入和风险能力
-> Agent / 钱包 / stablecoin / machine payment 能力
```

每个阶段都按同一组问题讲：

1. 当时 Stripe 解决了什么商业问题？
2. 它沉淀了什么可复用能力？
3. 这个能力在 AI 支付五层框架里对应哪一层？
4. AI 时代为什么会重新用到它？

### 6.4 阶段一：开发者接入能力

时间：2010-2014。

这一段不要写成：

> Stripe 成立于 2010 年，提供 API 支付。

要写成：

> Stripe 最早解决的不是“支付价格更低”，而是“开发者怎么把收款嵌进产品”。它把银行、支付机构、卡网络背后的复杂流程，封装成 API、文档、测试环境和 Dashboard。

沉淀能力：

- API-first
- SDK
- 文档
- 测试卡
- webhook
- Dashboard
- developer trust

对应第 3 章框架：

- 交易意图：让业务系统可以发起交易。
- 责任与审计：Dashboard、日志、webhook 让交易可追踪。

AI 时代复用：

> Agent 支付也需要同样的东西：不是给人看的页面，而是给软件调用的接口、测试环境、事件回调和状态追踪。

这一屏结论：

> Stripe 的第一层能力，是把支付变成可编程接口。

### 6.5 阶段二：平台和商户经营能力

时间：2015-2019。

核心讲法：

> 当 Stripe 服务的不再只是单一网站，而是平台、Marketplace、SaaS 和线下商户时，它开始进入商户经营层。支付不再是一笔收款，而是商户入驻、分账、订阅、计费、线下终端、风控和经营数据的组合。

沉淀能力：

- Connect
- Billing
- Radar
- Terminal
- Atlas
- platform onboarding
- merchant controls

对应第 3 章框架：

- 授权与身份：平台、商户、子账户、入驻关系。
- 规则与风控：商户风险、交易风险、欺诈检测。
- 资金与清结算：分账、结算、平台账户关系。

AI 时代复用：

> Agent commerce 不是单一消费者买单，而是要接入大量商户、平台和商品目录。商户控制、平台分账、风险规则和结算关系会再次变成核心。

这一屏结论：

> Stripe 的第二层能力，是从“支付接入”进入“商户经营系统”。

### 6.6 阶段三：金融运营能力

时间：2020-2022。

核心讲法：

> 随着客户全球化、平台化、金融动作变复杂，Stripe 继续向税务、身份、发卡、账户、融资、对账和全球运营扩展。它服务的已经不是一笔支付，而是一家公司如何管理收入、资金和风险。

沉淀能力：

- Tax
- Identity
- Issuing
- Treasury
- Capital
- Revenue Recognition
- reconciliation
- regional/local payment coverage

对应第 3 章框架：

- 授权与身份：Identity、KYC/KYB、账户关系。
- 资金与清结算：Treasury、Issuing、对账、结算。
- 责任与审计：税务、收入确认、争议、合规边界。

AI 时代复用：

> AI 业务往往全球化、高频、小额、用量波动大，背后需要税务、身份、发卡、融资、对账和收入确认能力。没有金融运营层，AI 支付只能是入口，不能成为基础设施。

这一屏结论：

> Stripe 的第三层能力，是把支付扩展成金融运营栈。

### 6.7 阶段四：AI 客户带来的收入和风险压力

时间：2023-2024。

核心讲法：

> AI 公司增长快、用量波动大、全球化早、欺诈和资源滥用风险高。它们对支付公司的要求，不只是收款，而是用量计费、收入管理、风控、税务和全球收款一起工作。

可以讲的内容：

- AI 公司需要按 token、usage、event、seat 或 outcome 收费。
- 成本和收入都跟用量强相关。
- 免费试用、盗用、fake signup、资源滥用风险变大。
- 全球客户带来税务、币种、支付方式和合规复杂度。

对应第 3 章框架：

- 交易意图：AI 服务的消费动作可能不是传统商品购买。
- 规则与风控：资源滥用和欺诈模式变化。
- 资金与清结算：用量计费、收入确认、全球结算。

AI 时代复用：

> 这一步让 Stripe 发现，AI 客户不是普通软件客户。它们把计费、风控、收入和基础设施能力的压力提前暴露出来。

这一屏结论：

> Stripe 的第四层能力，是在 AI 客户压力下重组收入和风险基础设施。

### 6.8 阶段五：Agent、钱包、stablecoin 和机器支付

时间：2025-2026。

核心讲法：

> 到这一阶段，AI 支付不再只是 AI 公司怎么收钱，而是软件代理、钱包、stablecoin、机器支付协议开始改变交易本身。Stripe 过去积累的 API、商户、风控、计费、身份和结算能力，被放到新的交易入口和结算方式里。

可以讲的内容：

- Agent commerce：交易入口从人操作页面，进入软件代理场景。
- wallet / Privy：软件和应用需要管理新的凭据和账户抽象。
- Bridge / stablecoin：结算轨道从传统卡和银行网络扩展。
- Metronome / usage billing：AI 服务的计费粒度变细。
- MCP / agent toolkit / machine payment：开发者接口继续变重要。

对应第 3 章框架：

- 交易意图：Agent 发起交易。
- 授权与身份：wallet、凭据、账户抽象。
- 规则与风控：机器行为和 token 风险。
- 资金与清结算：stablecoin、machine payment。
- 责任与审计：交易日志、协议、争议和责任边界。

这一屏结论：

> Stripe 的 AI 支付布局，不是从 AI 开始，而是从对象、接口、权限、风控和资金关系的设计缺口开始。

### 6.9 第 4 章主视觉

建议做“双轴能力累积时间线”：

横轴：

```text
2010-2014 -> 2015-2019 -> 2020-2022 -> 2023-2024 -> 2025-2026
```

纵轴：

```text
开发者接入
平台/商户经营
计费/收入运营
风控/身份/合规
资金/清结算
Agent/钱包/stablecoin/机器支付
```

每个节点必须有一个 proof tag：

- 证明可编程接口
- 证明商户经营层
- 证明金融运营层
- 证明 AI 客户压力
- 证明新交易入口和结算轨道

### 6.10 第 4 章验收标准

这章写完后，听众应该能说出：

> Stripe 不是突然做 AI 支付，而是把过去积累的交易、商户、计费、风控、资金和开发者能力，迁移到 Agent、钱包、stablecoin 和机器支付场景。

如果这章只是列年份和产品，就是失败的。

## 7. 第 5 章：LinkedIn 人员能力画像

### 7.1 章节任务

这一章回答：

> 这种能力栈需要什么样的人来做？

LinkedIn 不是“人才流向信号”这么泛。这里要分析的是 Stripe 当前在职人员的背景和能力图。

### 7.2 分析维度

看五类信息：

| 维度 | 看什么 |
|---|---|
| 岗位族群 | 工程、产品、风控、合规、数据、金融运营、企业销售、稳定币、AI 工具。 |

> LinkedIn 支持我们观察 Stripe 的人员能力结构。

## 9. 第 7 章：未来五年判断

### 9.1 核心判断

> Agent 支付会先过规则关，再过金融结果关。

意思是：

> 在大规模交易结果出现之前，行业会先解决授权、限额、风控、责任、结算和审计问题。

### 9.2 不能过度预测

不要写：

> 未来五年 Stripe 会成为 AI 支付最大赢家。

要写：

> 如果 Agent 支付要进入高频、高金额、企业级场景，金融交易设计语言会成为基础设施竞争焦点。Stripe 是值得观察的候选者之一。

## 10. 第 8 章：我们能学什么

### 10.1 落点

这章要把分享从 Stripe 拉回我们自己：

> AI 降低了功能实现成本，但提高了金融关系设计成本。

### 10.2 具体启发

1. 不要只看入口，要看交易闭环。
2. 不要只看产品名，要看对象、规则、账务和责任边界。
3. 不要只看 AI demo，要看它能否进入真实金融约束。
4. 不要只看技术实现，要看组织里有没有对应能力。
5. 不要只学 Stripe 做了什么，要学它如何长期把复杂金融动作产品化。

### 10.3 结尾句

> 所以这场分享最后不是问“我们要不要做 AI 支付”，而是问：当软件开始替人执行交易，我们有没有能力定义清楚谁能做什么、用谁的钱、在什么规则内、出错谁负责。
