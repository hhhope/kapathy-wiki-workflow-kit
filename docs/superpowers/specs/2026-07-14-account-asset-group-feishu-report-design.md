# 账户资产组下半年重点工作飞书材料设计

## 1. 设计目标

为 2026-07-15 组织调整会议形成一份可在 10—15 分钟内完成口述的飞书材料。正文服务管理者快速判断，折叠附件保留系统、事件、监管和交接证据。

材料不从“三件事”直接起笔，而按以下证据链推导：

> 组织职责 → 现有系统与实际支撑 → 能力缺口 → 建设优先级 → 三件重点事项 → 交接专项

## 2. Article Intent Contract

- **读者**：工程效能部负责人及各团队管理者。
- **读者需要形成的判断**：账户资产组实际职责比组织图中的七项更完整；下半年建设重点来自职责与现状的缺口；三件重点事项与移交专项边界清楚。
- **主线**：围绕支付账户这一价值锚点，规划未来账户与结算能力，以涅槃和代销验证业务结果，以稳定性、研发效能和团队能力保障持续交付。
- **非目标**：不逐个介绍 89 个应用；不按银行逐家复述银企通现状；不泛讲 AI 转型；不为计费、增值制造没有需求的建设任务；不把移交混入三件重点事项。
- **用户确认的判断**：账户分散是现状而非全量统一目标；计费和增值当前无需求暂不建设；分账、卡包以交接为主；保险 10 月下线并封存；稳定性与研发效率合并，并纳入团队建设。
- **证据边界**：研发效能沿用“上半年 13.5、下半年稳定到 15、争取进入前 10”的用户口径，不擅自解释指标名称或单位；GitLab 两个仓库的内部实现尚未核验，不据此作系统能力结论。

## 3. 选定输出形态

采用“上会正文＋折叠附件”的飞书结构。

- 控制在 10—15 分钟口述；
- 使用高亮块、引用块、ASCII 树状脑图、带优先级表格、任务清单和折叠块；
- 所有表格必须包含优先级、排序或阶段字段；
- 三件重点事项是正文中心，职责图和缺口表只用于推导。

### 折叠附件

- 海纳、分账、卡包交接明细；
- 保险下线与数据封存检查表。

## 5. 开场设计

### 标题

**账户资产组下半年重点工作与交接安排**

副标题：**从职责承接、能力缺口到重点建设**

### 首屏高亮块

> 组织架构定义了账户资产组的七项职责，但从现有系统和实际支撑看，我们承担的范围还包括对账、业务报表、备付金及非现场监管。下半年不会平均建设所有能力，而是围绕支付账户这一价值锚点，补齐面向未来的账户与结算能力，支撑重点业务成功，同时提升资金链路稳定性、研发效能和团队能力。

### 本次汇报回答四个问题

1. 组织调整后，账户资产组实际承担什么；
2. 对照现有系统，已经有什么、还缺什么；
3. 根据缺口，下半年为什么选择这三件重点事项；
4. 海纳、分账、卡包和保险如何完成交接或退出。

## 6. 职责与支撑脑图设计

正文只使用一张单中心、向右展开的 ASCII 树状脑图。脑图不再拆分“组织图职责”“遗漏职责”和“XMind 使用边界”，而是直接标记每项能力的真实状态：**已有、需要建设、需要交接、退出或暂缓**。

```text
账户资产组职责与支撑全景
│
├─ 账户服务【已有｜建设】
│  ├─ 现有：4.0、慧收钱、移企付、宝财通、宝户通
│  └─ 重点需求：涅槃账户、账户模板、记账与校验参数化、客户等级、账户关系
│
├─ 取现／结算／代发【已有｜建设｜交接】
│  ├─ 现有：多套清算、结算系统和任务
│  ├─ 重点需求：分账账户自助结算、定时结算、营业时间结算、账期和资金状态
│  └─ 交接：海纳结算能力
│
├─ 计费服务【已有｜交接】
│  └─ 交接：海纳计费；当前无新增建设需求
│
├─ 账户供应链【已有｜建设】
│  ├─ 现有：前置、银企通、account-gateway、YQT、OMS
│  └─ 重点需求：Agent 协作接入、银行差异封装、渠道兼容、电子户快速切换
│
├─ 分账／分润【已有｜重点需求｜交接】
│  ├─ 现有：分账核心、4.0 分润、慧收钱分润
│  └─ 重点：完成分账能力交接，支撑代销场景必要改造
│
├─ 卡包服务【已有实践｜交接】
│  └─ 重点：完成嵌入式账户实践交接，梳理外部账户纳管
│
├─ 对账支撑【已有｜交接】
│  ├─ 职责补充：组织图未体现；现有 14 个对账应用及渠道、交易、资金差异处理
│  └─ 交接：海纳对账能力
│
├─ 业务报表与经营支撑【已有】
│  └─ 职责补充：组织图未体现；现有 21 张业务报表及电子户沉淀收益等支撑
│
├─ 备付金与监管数据支撑【已有｜重点需求】
│  ├─ 职责补充：组织图未体现；现有 ACS、CFS、分类账、分户账和清算核验
│  └─ 重点需求：非现场检查、数据准备、回执、补报重报和差异整改
│
├─ 增值服务【无明确需求｜暂缓】
│
└─ 保险【退出】
   └─ 10 月下线并完成数据封存
```

脑图只承担三项任务：说清现有承载、标出重点需求、标明交接和退出。具体应用、银行和事件明细不在正文单独展开，统一放入折叠附件作为证据。

## 7. 能力缺口与优先级

优先级只围绕已经明确的需求、生产问题和交接责任，不从组织架构名称推导虚构建设任务。

| 优先级 | 重点缺口或需求 | 现状依据 | 下半年选择 | 对应重点事项 |
|---|---|---|---|---|
| P0 | 涅槃账户及支付账户能力 | 新场景需要账户模板、参数化记账与校验、客户等级和账户关系 | 在涅槃及相关新场景中形成并验证账户能力 | 产品规划与账户能力建设 |
| P0 | 代销及 SaaS 结算 | 需要分账账户自助、定时和营业时间结算 | 补齐账期、可结算资金状态和结算方式 | 产品规划与账户能力建设 |
| P0 | 涅槃、代销与分账业务成功 | 分账能力需要交接，重点项目需要账户、结算、对账共同支撑 | 完成交接并跑通重点业务端到端场景 | 重点业务交付与客户成功 |
| P0 | 非现场检查支撑 | 已承担 ACS、CFS、分类账、分户账、清算核验及监管数据准备 | 明确责任、数据口径、报送和差异整改闭环 | 重点业务交付与客户成功 |
| P0 | 资金链路稳定性 | 上半年已发生冻结未解、任务失效、大表慢查询和告警缺失等问题 | 处理资金异常、任务可靠性、容量风险和关键链路灾备 | 稳定性、研发效能与团队建设 |
| P1 | 银行接入与渠道复用 | 多家银行反复出现字段、状态、回调、超时和流程差异 | Agent 协作接入、渠道兼容封装和电子户切换 | 稳定性、研发效能与团队建设 |
| P1 | 团队知识与专业能力 | 新接系统多，业务和运行知识存在个人依赖 | 主备岗、培训、知识库、复盘和技术分享 | 稳定性、研发效能与团队建设 |
| 交接 P0 | 海纳计费、结算、对账 | 需要接生产运维和必要业务改造，且与汶达存在职责交叉 | 形成清单、RACI、跟班、独立运行和验收 | 移交专项 |
| 交接 P1 | 分账、卡包 | 能力已有，但团队需要接清规则、数据、任务和异常处理 | 完成交接并支持明确的业务改造 | 移交专项 |
| 暂缓 | 计费新能力、增值服务 | 当前没有明确新增需求 | 不主动建设 | 明确不做 |
| 退出 | 保险 | 已明确 10 月下线 | 完成下线和数据封存 | 退出专项 |

## 8. 三件重点事项

三件事形成递进关系：规划未来能力 → 用重点业务验证结果 → 以稳定性、效能和团队能力保障持续交付。

### 8.1 产品规划与账户能力建设

核心判断：不做全部存量账户的统一改造，围绕涅槃、代销等明确场景，把账户模板、记账与校验参数、客户等级和结算方式做成可复用能力。

| 优先级 | 重点方向 | 下半年建设内容 | 预期结果 |
|---|---|---|---|
| P0 | 涅槃账户与支付账户模板 | 定义账户类型、层级、用途、客户等级、资金属性和生命周期 | 在涅槃等明确场景落地验证 |
| P0 | 记账参数化 | 逐步抽离借贷方向、资金流向和记账条件 | 业务规则变化减少核心代码改动 |
| P0 | 校验参数化 | 参数化客户身份、账户状态、产品权限、余额和限额 | 支持差异化账户能力组合 |
| P0 | 结算产品规划 | 支持自助、定时和营业时间结算 | 支撑代销和 SaaS 资金经营 |
| P1 | 外部账户纳管 | 梳理银行电子户、卡包、嵌入式账户与内部账户关系 | 明确识别、关联、查询、切换和退出方式 |
| 暂缓 | 计费、增值 | 当前没有明确新增需求 | 保持运行，不主动建设新平台 |

本事项交付账户能力地图、账户模板 V1、记账与校验参数模型、结算产品方案和建设边界。

### 8.2 重点业务交付与客户成功

核心判断：重点项目不能只验收接口和上线时间，要验证账户能力是否真正支撑业务经营和客户使用。

| 优先级 | 重点方向 | 下半年重点 | 成功标准 |
|---|---|---|---|
| P0 | 涅槃项目 | 支撑账户、会员、支付、结算及迁移链路 | 关键场景端到端可用并稳定运行 |
| P0 | 代销与分账场景 | 完成分账能力交接，支撑参与方账户、分账账户、退款、资金状态和结算方式 | 跑通交易到分账、结算和异常处理闭环 |
| P0 | 产品规划支持 | 研发前置参与账户结构、结算方式、资金路径和异常方案 | 关键规则在开发前确定 |
| P0 | 上线与监管支撑 | 联动对账、业务报表、备付金及非现场检查的数据准备和差异处理 | 上线后资金能核对，监管数据能说明，差异有闭环 |
| P1 | 客户问题治理 | 聚焦开户、资金使用、结算和查询问题 | 问题有 Owner、结论和治理结果 |
| P1 | 能力沉淀 | 沉淀账户、结算和异常处理方式 | 后续业务可以复用 |

客户成功不使用抽象口号，直接看五个结果：能开户和使用账户、能正确入账分账结算、能按经营需要选择结算方式、异常能解释处理、已形成的能力能在后续场景复用。

### 8.3 稳定性、研发效能与团队建设

核心判断：稳定性、效率和团队能力是一套保障账户资产能力持续交付的工程基本盘。

#### 稳定性

| 优先级 | 上半年事件暴露的问题 | 下半年必须解决 | 结果 |
|---|---|---|---|
| P0 | 冻结未解、结算卡住、退款和调账依赖人工 | 建立发现、重试、补偿、核对和审计闭环 | 资金异常不再只依赖人工查库 |
| P0 | 任务未执行、锁不释放、节点变化后任务失效 | 建立任务监控、幂等、续跑和人工重放能力 | 任务失败能够及时发现和恢复 |
| P0 | 大表、慢 SQL、归档数据影响生产 | 治理高风险表、索引、查询和归档策略 | 核心容量风险受控 |
| P0 | 系统、数据库、机房或银行异常后的恢复不清楚 | 完成关键资金链路高可用和灾备验证 | 形成方案、手册和演练记录 |
| P1 | 告警不准、失败原因不落库、依赖运营反馈 | 建立面向资金结果的业务监控 | 能定位影响对象和处理路径 |

#### 研发效能

| 优先级 | 方向 | 上半年基础 | 下半年推进 |
|---|---|---|---|
| P0 | 效能目标 | 13.5 | 稳定到 15，争取进入前 10 |
| P0 | 银行接入 | 文档、映射、适配和测试主要依赖人工 | Agent 辅助文档解析、字段映射、适配代码和契约测试 |
| P0 | 渠道封装 | 银行差异反复影响上游 | 渠道层统一兼容和封装，减少上游感知 |
| P1 | 电子户切换 | 切换涉及多系统和人工操作 | 建立配置化切换、验证和回退机制 |
| P1 | 研发过程 | 设计、验证和经验沉淀不稳定 | 强化方案评审、影响分析、测试验证和发布检查 |

#### 团队建设

| 优先级 | 建设方向 | 下半年动作 | 预期变化 |
|---|---|---|---|
| P0 | 重点系统主备 | 账户、结算、分账、对账建立主备岗 | 减少个人单点 |
| P0 | 业务能力培训 | 覆盖账户、结算、分账、对账、备付金和非现场监管 | 团队能解释完整资金链路 |
| P0 | 知识库沉淀 | 沉淀系统地图、规则口径、异常案例、运维手册和银行知识 | 交接和故障处理不依赖口头传递 |
| P1 | 复盘机制 | 复盘资金事件、重大方案和重点项目 | 从修复单点问题升级为治理同类问题 |
| P1 | 技术氛围 | 设计评审、交叉 Review、技术分享和方案 Demo | 形成讨论难题和共同承担结果的氛围 |

## 9. 移交专项设计

移交在三件重点事项之后单列，不作为第四件建设事项。

| 优先级 | 移交事项 | 交接重点 | 验收结果 |
|---|---|---|---|
| P0 | 海纳 | 计费、对账、结算、`xx-base-manager`、`xx-oms-web`，以及与汶达的需求、研发、数据、运维、事故边界 | 账户组能独立运维并完成必要业务改造 |
| P0 | 分账 | 规则、代码、配置、数据、任务、监控和异常处理 | 团队能够独立定位和处理问题 |
| P1 | 卡包 | 嵌入式账户实践、外部账户关系和现有系统 | 完成交接并支撑外部账户纳管设计 |
| 退出 | 保险 | 应用、数据、任务、接口和审计查询 | 10 月下线并完成数据封存 |

### 交接节奏

| 优先级 | 阶段 | 重点动作 | 输出 |
|---|---|---|---|
| P0 | 7 月：盘点与定责 | 系统、权限、任务、接口、数据、监控、问题和 RACI | 移交清单、责任矩阵 |
| P0 | 8 月：跟班与共担 | 共同值守、共同变更、共同处置事件 | 跟班记录、问题台账 |
| P0 | 9 月：独立运行 | 独立值守、独立定位、独立完成必要改造 | 交接验收记录 |
| 退出 | 10 月：保险退出 | 停止任务和接口，完成数据封存及查询审计方案 | 下线确认、封存清单 |

## 10. 收尾设计

使用高亮块收束：

> 下半年，账户资产组不是平均维护更多系统，而是围绕支付账户价值锚点，规划并建设账户与结算能力，以涅槃和代销验证业务成功，以稳定性、研发效能和团队能力保证持续交付，同时按计划接稳海纳、分账和卡包，完成保险退出。

## 11. 实施与验证边界

- 飞书正文必须保持上述章节顺序，不得从三件事直接起笔；
- ASCII 职责图保持单中心树状层级，不改成关系网；
- 所有表格带优先级、阶段或排序字段；
- ACS、CFS、备付金和非现场监管不压缩为普通 BI；
- 正文口述试跑需控制在 10—15 分钟；
- 折叠附件不得反向挤入正文；
- 每项重点必须写明现状依据、具体动作和可核验结果；删除“全面赋能”“体系化升级”等无法由材料证明的表述；
- 对尚未具备、尚未交接或没有需求的能力直接标注，不用规划话术掩盖；
- 写入飞书前需要用户明确批准；写入后必须回读核验。
