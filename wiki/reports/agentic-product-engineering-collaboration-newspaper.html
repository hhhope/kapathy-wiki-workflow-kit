AI Agent 时代产研协作观察报

262 个 source entries 之后，行业真正争论的不是工具，而是谁定义目标、谁承担判断、谁审查结果、谁拥有作业系统。

头版判断

产研协作正在从人力流水线，变成人机作业系统。

Agent 不是把工程师变快的插件。它把 ticket、spec、PR、CI、eval、wiki 变成可执行对象。人不再只负责把上下文传给下一个人，而要负责目标、边界、判断和后果。

旧问题：怎么让人更快交付？

产品、设计、工程、测试按顺序接力。上下文靠会议和文档搬运，质量靠末端验收兜底。

新问题：怎么让系统可执行、可审查、可沉淀？

人定义目标和判断边界，agent 执行和自证，结果进入 PR、review packet、eval、wiki、rules。

行业在争什么

surface debate, internal collaboration question

争论的表层是 Agent，底层是公司内部协作怎么重新分工

行业会把问题说成“代码会不会被解决”“PM 会不会消失”“小团队会不会替代大组织”。真正落到公司里，问题只有四个：谁定义目标，谁补全上下文，谁执行中间工作，谁对结果负责。

Real Question

落到公司内部，其实是四个分工问题

Agent 让执行变便宜，但也把含糊目标、弱 owner、低质量验收暴露得更快。真正要重分的是目标、上下文、执行和责任。

谁定义目标 谁补全上下文 谁执行中间工作 谁对结果负责
行业争论可以压成一条线：执行越自动化，目标、判断、审查和责任越不能被省掉。

证据边界：公开讨论和本地源池只能支撑争议结构。真正的公司结论，需要回到具体业务流、具体 owner、具体风险等级和具体验收样本。

公司内部协作正在变成一只哑铃

judgment side, execution side, collaboration bridge

一端是目标、判断和责任，一端是可执行、可验证、可回放的系统能力

传统协作把很多中间工作放在人身上：解释需求、补上下文、追进度、兜质量。Agent 进入后，这些工作不会凭空消失，而是被重新拆到两端。人的一端更重，系统的一端也更重。

internal dumbbell

Human Side

人的判断端

目标、非目标、用户取舍、风险承受、验收标准、发布判断，不能被 Agent 接管。

谁是 owner 什么不能做 什么才算过关
Bridge

产研协作桥

spec eval review packet wiki rules PR / issue

把判断翻译成可执行上下文，把执行结果翻译成可审查证据。

System Side

系统执行端

找上下文、拆任务、生成初稿、跑验证、整理证据，变成可排队、可审查、可复用的执行单元。

权限和审计 回归测试 知识写回
Old Handoff

传统协作链靠人把上下文一段段搬过去

PM 到 Design 到 Eng 到 QA，协作能跑起来，但上下文容易丢，责任也容易在交接里变模糊。

PM->Design->Eng->QA

人不是退场

转述型中间劳动被压缩，判断型中间责任被抬高。人的位置从搬运上下文，转向定义边界和审结果。

系统端必须变强

执行层变快以后，系统必须承担权限、日志、测试、回滚、证据打包和知识写回。

中杆不能断

spec、eval、review packet、wiki、rules、issue 和 PR 是中间那根杆。杆不结实，两端都会变成孤岛。

这里的重点不是说组织会变扁，而是说协作的承重点变了：人的判断端和系统执行端同时变重，中间必须有可执行、可审查、可沉淀的连接物。

章节 takeaway：AI 时代的内部协作不是少一层人，而是把传话链改造成连接判断和执行的作业桥。

作业系统变了

from handoff pipeline to executable work surface

变的不是工具入口，而是公司把工作交出去、收回来、审清楚的方式

过去的产研协作像流水线：产品写需求，设计补体验，工程拆实现，测试做兜底，管理者靠会议追状态。每次交接都会丢一部分上下文，真正的判断常常藏在人脑里。

旧作业系统靠交接维持

After

新作业面把中间工作变成可执行上下文

人把目标、边界、样例、反例、权限和验收标准包装清楚；Agent 承担检索、拆解、生成、实现、验证和证据整理。

可调用：工作能被触发和排队 可审查：输出带依据、风险和验证 可回放：过程留下输入、工具和结果 可沉淀：失败写回 rules / tests / wiki / skill
警告：Agent 可以执行中间工作，但不能替公司决定目标、取舍、责任和风险承受。没有 owner 的 Agent queue，只会把混乱排得更整齐。

章节 takeaway：Agent 没有发明中间工作，它把中间工作的承载方式从人脑和会议，改成可执行、可审查、可沉淀的作业系统。

Agent 把中间执行层变成可审查循环

Agent 最有价值的地方不是一次性给答案，而是把中间执行层变成可审查循环：目标进去，证据出来，失败能写回系统。

reviewable loop
not autopilot
01

人定目标

目标、非目标、用户价值、风险边界和验收标准先写清楚。

02

可执行包

背景、边界、示例、反例、数据入口、测试方法、权限范围进入上下文。

03

Agent Queue

检索资料、拆步骤、改代码、跑检查、整理证据，按边界工作。

04

Review Packet

输出带上变更点、依据、验证结果、失败项、风险和待判断问题。

05

系统写回

失败写回新测试、新规则、新示例和新知识页，下一轮少踩同一个坑。

闭环不是全自动

Agent 不能自己批准自己。高风险节点必须有人审、可追责、可回滚。没有审查和写回，它只是更快地产出一次性材料。

中间执行层从“人靠经验转述”变成“系统可调用的工作循环”。人的位置不是消失，而是上移到目标、边界、审查和责任。

章节 takeaway：有审查和写回，Agent 才开始变成公司的作业系统；没有审查和写回，它只是更快的内容生成器。

现有公司的人该怎么做

role-by-role operating change
CEO / GM

别把 AI 当采购项目

  • 选一个真业务瓶颈做 30-60 天试点。
  • 明确质量、风险、成本和责任边界。
  • 用流程结果考核，不用“用了多少 AI”考核。
Product / PM

从需求转述者变成判断 owner

  • 写清目标、非目标、用户场景和验收标准。
  • 把 ticket/spec/wiki 做成 agent 可执行上下文。
  • 保留取舍权，不能把产品判断外包给模型。
Designer / Research

把体验判断变成可测试样本

  • 沉淀用户语境、反例、边界场景和体验红线。
  • 用原型和 review packet 审 agent 产物。
  • 把“像不像人话”变成示例和检查项。
Engineer / TL

从写代码扩展到管理执行系统

  • 设计工具权限、上下文入口、测试和回滚。
  • 审查 agent 输出是否真的满足 spec。
  • 把失败写回 eval、lint、guardrail、skill。
QA / Data / Ops

把反复出错的地方变成 eval

  • 从末端兜底转向前置风险样本库。
  • 把缺陷、异常、客诉、合规点结构化。
  • 用可复跑检查证明 agent 没有只会演示。
Manager / HR

重写岗位边界和成长路径

  • 区分可自动化执行和必须人类判断的工作。
  • 训练员工写上下文、审证据、管风险。
  • 调整绩效：看结果质量、系统沉淀和协作吞吐。

我们应该怎么做

local operating principles

三条原则

  • 目标人定。业务目标、用户价值、优先级、风险承受度不能交给 agent。
  • 过程可委托。检索、整理、生成、实现、验证、回放可以交给 agent。
  • 结果可审计。所有输出必须进入 PR、review packet、eval、wiki、日志这类可追踪对象。

第一条试点链路

  • 从会议材料、文章或需求进入。
  • 沉淀成 spec / wiki / issue。
  • agent 产出草稿、代码改动或 review packet。
  • 人审查判断，失败写回规则、测试、skill、wiki。
