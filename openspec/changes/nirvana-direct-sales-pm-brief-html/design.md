## Context

当前仓库内已经存在多份涅槃相关材料，但用途和表达层次混杂：

- `nirvana-handover-account-owner.md` 更偏承接与风险交接
- `nirvana-phase1-pm-review.md` 已经开始承接项目管理主表，但语言仍混有分析口径
- `nirvana-phase1-leadership-brief.md` 已经有领导摘要雏形，但信息密度、对比关系和视觉呈现还不足
- `inbox/nirvana/preview .html` 提供了甘特图和能力地图的视觉参考，但还不是针对“直销模式下一期复盘和领导汇报”的表达结构

这次变更的约束很明确：

- 只聚焦直销模式下一期，不扩展到全量产品或其他模式
- 输出必须能直接服务复盘和领导汇报，不再使用泛化分析语言
- HTML 必须和内容主稿是同一套口径，不能出现“页面好看但结论说不清”的问题

主要干系人包括项目负责人、产品一号位、技术一号位、测试一号位，以及需要听汇报的管理层。

## Goals / Non-Goals

**Goals:**

- 建立一份以项目管理语言组织的直销模式下一期主稿，固定输出结构为：承诺接口、最小可交付路径、能力覆盖判断、关键时间节点、当前交付约束、资源诉求、待拍板事项。
- 让主稿与交接稿形成清晰分工：交接稿负责承接视角，PM 主稿负责复盘和汇报视角。
- 生成一版高对比、高信息密度的 HTML 汇报页，突出时间、范围、能力覆盖和资源动作之间的对比关系。
- 统一表达口径，使 markdown 主稿和 HTML 视图共享同一套管理语言和结论。

**Non-Goals:**

- 不在这次变更中新增业务事实、改写源材料结论或补造不存在的排期数据。
- 不在这次变更中扩展到非直销模式、M3 全量范围或其他项目。
- 不在这次变更中引入新数据源、自动化同步或复杂前端框架。

## Decisions

### Decision: 以 PM 主稿作为唯一内容基线

HTML 不直接从交接稿拼接，也不从多个文档混拼；先将 `nirvana-phase1-pm-review.md` 固化为唯一管理口径基线，再从该基线抽取 HTML 所需板块。

Why:

- 交接稿的职责是帮助承接人识别风险与未完成项，不适合作为领导汇报基线。
- 如果 HTML 直接混用交接稿与周报材料，会再次产生口径冲突。

Alternative considered:

- 直接以 `nirvana-handover-account-owner.md` 为基线扩展领导页。
  - Rejected，因为交接视角天然偏“承接和风险”，不偏“承诺、完成度、资源诉求”。

### Decision: 用项目管理语言替换分析语言

文案统一使用“当前偏差”“未闭环项”“交付约束”“资源配置约束”“需管理层拍板事项”等表达，不再以 `gap` 为主标题语言。

Why:

- 用户的使用场景是复盘和领导汇报，管理语言更适合当场表达。
- 分析语言容易把问题讲散，不能直接落到动作和决策。

Alternative considered:

- 保留原 `gap/risk` 结构，仅做局部润色。
  - Rejected，因为结构问题比措辞问题更大。

### Decision: HTML 采用强对比的单页密集布局

HTML 采用单页结构，重点分成四个对比区：

- 承诺范围 vs 当前可交付范围
- 对客最小路径 vs 当前未闭环项
- 直销当前能力 vs 代销目标能力
- 时间节点 vs 当前偏差
- 资源约束 vs 当前诉求

Why:

- 用户明确要求高对比、高信息密度、适合张口汇报。
- 该结构有利于快速回答“承诺了什么、做到了什么、还缺什么、要什么资源”。

Alternative considered:

- 延续现有参考 H5 的长篇叙事结构。
  - Rejected，因为信息层次不够锋利，汇报时不容易聚焦。

### Decision: 用“直销对标代销差距图”替代“模式能力抽象”

HTML 不再停留在“模式能力抽象”这类内部表达，而是明确展示“直销当前能力、代销目标能力、当前差距、对客影响和一期处理口径”。

Why:

- 用户真正要看的不是抽象层次，而是“差什么、差多远、这次接不接”。
- 如果只展示直销能力，不展示相对代销的差距，就无法解释共性底座复用与模式差异边界。
- 该视图能直接回答：直销当前已经追平哪些能力、哪些只是复用底座、哪些差距会影响对客表达。

Alternative considered:

- 保留“模式能力抽象”表，仅增加几列说明。
  - Rejected，因为读者仍然看不出差距强弱和一期处理口径。

### Decision: 将能力覆盖率保留为管理口径判断，而不是伪精确计算

继续使用“稳定可对客表达 / 已进入承接但未到可对客承诺 / 仍缺稳定边界或承接”的分层表达，仅在必要时用近似比例辅助，而不构造精确统计模型。

Why:

- 当前材料是项目资料，不是机器可核算的接口交付数据库。
- 伪精确数字会削弱汇报可信度。

Alternative considered:

- 对所有接口逐个赋权并计算完成率。
  - Rejected，因为输入基础不稳定，输出会产生误导。

### Decision: 主甘特工作流必须优先使用源排期中的业务对象名

直销一期 HTML 的主甘特工作流必须优先沿用源排期中的业务对象或模块名称，不再允许用汇报者自行抽象的阶段名替代真实工作流。

Why:

- 涅槃这次反复偏移的根因之一，就是把真实排期对象改写成“开通准备”“支付结果反馈”“协议支付分账能力”这类二次抽象名，导致页面和源排期断开。
- 领导汇报场景下，工作流名称首先要帮助读者识别“业务对象是什么”，而不是帮助作者做归类。

Alternative considered:

- 允许用管理抽象名统一压缩工作流。
  - Rejected，因为会削弱与源排期的一一映射关系，导致复盘时难以追责和核表。

### Decision: 状态语义必须逐项服从源排期，不得把“已排期”写成“已推进”

甘特图中的状态颜色和状态文案必须尊重源排期的真实状态。源排期为 `未开始` 的事项，即使已有预计日期，也不得绘制为进行中。

Why:

- 这次 `基础退款`、`分账` 两条线已经暴露出问题：有时间点不等于已经启动。
- 项目汇报里，状态失真比文案不美观更危险。

Alternative considered:

- 只要已有排期时间，就允许渲染成“推进中”。
  - Rejected，因为会把“计划存在”误写成“执行发生”，直接扭曲项目判断。

### Decision: 原业务里程碑和当前功能排期基线必须拆开表达

当业务总里程碑已经明显偏离时，HTML 和 markdown 不得继续把它写成当前时间基线，必须显式区分“原业务里程碑”和“当前功能排期基线”。

Why:

- 涅槃这次 `2026-06-30` 已经不能直接代表当前交付基线。
- 如果不拆开表达，领导会误以为页面中的时间判断都建立在同一套可信基线上。

Alternative considered:

- 继续把业务总里程碑作为统一时间基线使用。
  - Rejected，因为它已失去当前控制价值，只适合作为原承诺背景。

### Decision: 账户承担资金承接职责时必须进入主甘特

如果输入排期中账户承担资金承接、结算、冻结、查询等职责，账户必须作为主工作流进入甘特图，而不能只留在技术建设表或能力地图中。

Why:

- 账户在直销一期里不是外围底座，而是支付、退款、分账的共同承接面。
- 这次如果不把账户放进主甘特，页面会错误地呈现出“交易和退款在推进，但资金承接没有主排期”的断层。

Alternative considered:

- 账户只在技术建设表出现，主甘特只展示业务工作流。
  - Rejected，因为会掩盖资金承接和结算能力的真实排期压力。

### Decision: 口述信息必须按“当前事实 / 方向补充 / 待澄清”三层分开处理

来自用户口述、会话补充或会议现场澄清的信息，不得默认都进入直销主甘特。必须先判断它属于哪一层：

- 当前事实：已有源表或用户明确要求按当前汇报事实展示，可进入主甘特或顶部关键节点
- 方向补充：可以帮助解释业务节奏或后续规划，只能进入说明区或能力对标区
- 待澄清：用户已明确表示“没数据”“待补充”“后续确认”的内容，只能显式标记为待澄清，不能被写成既成排期

Why:

- 这次 `会员进度`、`宝财通`、`慧收钱`、`聚合收单` 等信息多次发生层级混写，根因就是没有把“能提到”和“能进入主甘特”分开。
- 直销一期主甘特是当前控制工具，不是所有业务方向的容器。

Alternative considered:

- 只要用户口头提到，就默认进主甘特。
  - Rejected，因为会把方向性信息误写成当前执行事实。

### Decision: 直销主甘特只展示当前直销主线，代销目标和会员进度只在有数据时进入对比区

主甘特只展示当前一期直销模式的主线工作流。代销目标能力、会员进度、后续模式差异等信息，只有在存在明确数据且对当前判断有帮助时，才能进入能力对标区；没有数据时必须标记为待澄清。

Why:

- 用户当前要讲的是“直销模式一期”，不是模式全景长图。
- 代销和会员信息如果混进主甘特，会直接稀释当前排期判断，导致“当前主线”失焦。

Alternative considered:

- 代销目标和会员进度直接并排进入主甘特。
  - Rejected，因为会打乱当前一期时间轴，也会造成“当前主线”和“后续能力”混表。

### Decision: 甘特条标签必须是可汇报的业务名词，禁止缩写尾标和无解释节点

甘特条和尾部标签必须使用业务可读、管理可讲的标签，不得出现 `统户`、`09-30节点`、`M3延续`、`微信` 这类脱离上下文的缩写或尾标。

Why:

- 这类标签在投屏场景里没有解释空间，读者无法判断是对象、节点还是状态。
- 用户已经明确要求业务、技术、管理三类词汇分别使用专业名称，不接受临时缩写。

Alternative considered:

- 为了节省空间允许使用任意缩写。
  - Rejected，因为会快速降低投屏可读性和汇报可信度。

## Risks / Trade-offs

- [Risk] 现有材料之间日期和状态口径并不完全一致 → Mitigation: 统一以 `截至 2026-04-15` 的 PM 主稿为汇报基线，冲突处明确写成“状态口径未统一”而非自行消解。
- [Risk] HTML 追求视觉冲击后丢失准确性 → Mitigation: HTML 只展示已在 PM 主稿中明确写出的结论，不新增推断。
- [Risk] 交接稿和 PM 主稿继续职责混淆 → Mitigation: 在主稿和 HTML 中固定使用“承诺、可交付、约束、资源、拍板”结构，不复用交接稿目录。
- [Risk] 用户对密度和对比要求高，页面容易过度拥挤 → Mitigation: 通过卡片区、表格区、对比区分层，优先压缩表述而不是压缩事实。
- [Risk] 直销与代销差距表达如果过度抽象，会失去管理价值 → Mitigation: 对每个领域固定展示“当前能力 / 目标能力 / 差距 / 对客影响 / 一期处理口径”。
- [Risk] 主甘特再次偏离源排期对象与状态 → Mitigation: 固定“业务对象命名优先”和“状态逐项服从源排期”两条规则，并在最终自检中逐条核表。

## Migration Plan

1. 在 OpenSpec 下固化直销一期 PM 主稿与 HTML 汇报能力的规格。
2. 调整 `wiki/reports/nirvana-phase1-pm-review.md`，统一项目管理语言与直销一期边界。
3. 视需要同步调整 `wiki/reports/nirvana-phase1-leadership-brief.md` 和索引页。
4. 新增单页 HTML 汇报页，基于主稿抽取固定板块。
5. 自查 markdown 与 HTML 的口径一致性，确保核心数字、日期、结论一致。

Rollback:

- 如果 HTML 表达效果不达标，保留 markdown 主稿不回退，只回退 HTML 文件。
- 如果口径结构需要再次调整，以 PM 主稿为唯一修改入口，再重新派生 HTML。
