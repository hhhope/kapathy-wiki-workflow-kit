八、从背后看出什么

1. 这不是单项目开发，是跨域闭环

账户、支付、商业应用和测试同时高占用，说明需求本质是账户模型、资金流、交易接入、报表/查询和验证共同闭环。

2. 高峰不是“写代码”，而是复杂闭环被压缩

W16-W21 连续高位，说明 AI 或规范化编码即便提升写代码速度，也会把更多时间推到集成、修复、验证和主干合入。

3. 代码量不能单独解释投入

代码净增高的项目不一定修复窗口最长；真正需要管理的是代码生成后到主干稳定之间的返修时间和测试占用。

4. 测试后移是风险信号

测试部在 W19-W21 占用上升，意味着问题发现和回归集中在后段；如果需求边界继续变化，后段会继续吸收成本。

5. main 合入日不是项目完成日

主干最后合入只能说明代码进入主线；真正完成还要看线上验证、失败写回、回归结论和后续缺陷是否收敛。

6. 研发投入要从人日升级到闭环指标

建议后续同时追踪：周人日、代码净增、fix 窗口、测试回归占用、主干合入后缺陷数和失败写回质量。

结论

第一，分账核心改造的真实投入是闭环投入：主工单 311.65 人日，加独立任务 44.75 人日，总占用 356.4 人日，其中研发四组 261.45 人日，测试 47.5 人日。

第二，代码生成/提交不是瓶颈的全部：Excel 口径净增 +51,271 行，本地 Git 源码口径 +48,729 / -17,059，但本地 Git 显示 746 次提交、141 次 AI/规范化候选、97 条返工/重构信号。

第三，管理上真正要盯的是“写完之后”：AI/规范化提交可以提高产出速度，但如果需求、验证、主干合入和失败写回没有同步工程化，高代码量会转化成重构、修复、测试、主干合入和 CR 审查的持续占用。

证据边界

数据来自 Excel 工单、Excel 代码量页和本地 `/mnt/d` Git 仓库。`account-book-query` 本地映射未确认；`其他独立任务工单` 没有日期，不进入周曲线；AI 代码量按提交规范做代理识别，不作绝对归因。
