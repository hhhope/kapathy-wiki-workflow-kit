# 贷款还款运营增收工作台 PRD

## Trigger

用户要求不只记录一个分析页，而是把贷款还款订单数据场景完整做下去。本文负责执行层 PRD 和版本拆解。

## 1. Summary

贷款还款运营增收工作台面向贷款机构、贷款科技服务商和贷后运营团队。产品基于放款订单、还款计划、还款订单、渠道流水和清算结果，帮助客户提升还款成功率、恢复失败还款、识别复贷机会、降低对账和渠道损耗。

第一版不做大而全的数据平台，也不做自动授信或征信服务。第一版做订单事实层、历史回测和一个还款周期的运营试点。

## 3. Background

很多贷款机构已经有放款和还款订单，但这些数据分散在贷款核心、支付渠道、清算对账、贷后运营、客服系统中。客户通常只能看到单笔订单状态，难以把订单变成经营动作。

现在值得做的原因：

- 贷款机构增长从获客转向存量经营和贷后精细化；
- 还款失败、逾期恢复、复贷转化、对账差错都能直接影响利润；
- 支付和清算链路已有订单数据，可以先做回放验证；
- AI 和数据分析能力能降低归因、分层、策略生成的门槛。

## 4. Objective

目标：

> 在不出售个人明细数据、不触碰未经确认的征信边界前提下，把客户已有放款、还款、对账订单转化为可收费的还款运营增收能力。

### Key Results

试点阶段 KR：

1. 完成 2 个存量客户的字段盘点和历史订单回测。
2. 至少 1 个客户完成一个完整还款周期试点。
3. 在试点客户中证明至少 1 个可量化结果：
   - 失败后恢复率提升；
   - 复贷候选转化提升；
   - 对账人工时长下降；
   - 差错追回金额可见；
   - 渠道成本下降。
4. 建立一份合规用途清单，明确哪些能力可上线、哪些能力需审批、哪些能力禁止。

## 5. Market Segments

### Primary Segment: 消费金融 / 小贷 / 助贷平台

使用者：

- 贷后运营负责人；
- 产品运营负责人；
- 财务对账负责人；
- 数据分析负责人；
- 风控负责人。

约束：

- 订单量大；
- 系统多；
- 对还款恢复和复贷增收敏感；
- 合规审查不能绕过。

### Secondary Segment: 贷款科技服务商 / 贷后服务商

使用者：

- 解决方案负责人；
- 客户成功负责人；
- 数据产品负责人。

约束：

- 需要白标；
- 需要多租户；
- 需要给多个贷款机构解释指标和归因。

### Later Segment: 银行零售信贷部门

使用者：

- 零售信贷运营；
- 风险管理；
- 财务清算；
- 客服管理。

约束：

- 采购周期长；
- 数据安全要求高；
- 早期适合从对账、看板、客户服务切入。

## 6. Value Propositions

### Job 1: 我想提升还款成功率

客户收益：

- 更快知道失败原因；
- 更准确选择重试或人工介入；
- 更少逾期和催收成本。

产品能力：

- 失败原因分层；
- 重试策略建议；
- 渠道成功率分析；
- 失败后恢复报表。

### Job 2: 我想合规经营结清和稳定还款客户

客户收益：

- 不再全量粗放召回；
- 能解释为什么这个客户进入候选池；
- 能看到触达后的转化和风险表现。

产品能力：

- 结清客户池；
- 稳定还款客户分层；
- 复贷候选规则；
- 触达记录和退订状态；
- 转化和早期逾期跟踪。

### Job 3: 我想减少对账和渠道损耗

客户收益：

- 更少人工查账；
- 更早发现渠道、清算、手续费异常；
- 更容易向资金方和渠道解释差异。

产品能力：

- 订单事实层；
- 差错清单；
- 渠道成本看板；
- 清算周期分析；
- 分润核验。

## 7. Solution

### 7.1 User Flow

1. 客户上传或接口接入历史订单样本。
2. 系统完成字段映射和数据质量检查。
3. 系统生成订单事实层：
   - 放款订单；
   - 还款计划；
   - 还款订单；
   - 渠道流水；
   - 清算结果。
4. 系统输出三个工作区：
   - 还款失败挽回；
   - 复贷 / 续贷候选；
   - 对账与渠道成本。
5. 客户确认策略、授权和触达边界。
6. 试点运行一个还款周期。
7. 系统生成增量价值报告。

### 7.2 Key Features

#### Feature A: Field Inventory And Data Quality Check

目标：

- 让客户知道现有数据能不能支持后续产品。

功能：

- 字段映射模板；
- 必填字段缺失检查；
- 状态枚举检查；
- 订单链路匹配率；
- 失败原因覆盖率；
- 脱敏和用途记录。

验收：

- 能输出客户字段盘点报告；
- 能标记无法用于回测的字段缺口；
- 能区分可用、需清洗、不可用字段。

#### Feature B: Repayment Order Fact Layer

目标：

- 把分散订单变成统一客户还款生命周期。

功能：

- 放款订单入库；
- 还款计划入库；
- 还款订单入库；
- 渠道流水入库；
- 清算结果入库；
- 订单关联和状态对齐。

验收：

- 同一客户、同一贷款、同一期还款可以被串起来；
- 能识别还款成功未销账、渠道退回、冲正、重复订单；
- 能输出订单链路覆盖率。

#### Feature C: Repayment Recovery Workbench

目标：

- 提升失败订单恢复率。

功能：

- 失败原因分布；
- 失败后恢复路径；
- 重试建议；
- 渠道成功率；
- 宽限期挽回队列；
- 恢复金额归因。

验收：

- 能生成待挽回订单清单；
- 能记录策略动作；
- 能统计策略后 24/72 小时恢复金额。

#### Feature D: Lifecycle Revenue Workbench

目标：

- 找到可合规经营的结清和稳定还款客户。

功能：

- 结清客户池；
- 提前还款客户池；
- 稳定还款客户池；
- 近逾期恢复客户池；
- 触达授权和退订状态；
- 复贷转化和早期逾期跟踪。

验收：

- 候选池每条记录都有进入原因；
- 未授权或退订客户不能进入触达队列；
- 复贷结果能回写。

#### Feature E: Reconciliation And Channel Cost Workbench

目标：

- 降低对账、清算和渠道损耗。

功能：

- 手续费分析；
- 渠道成功率；
- 清算周期；
- 差错订单；
- 分润差异；
- 人工处理队列。

验收：

- 能输出差错清单；
- 能按渠道和产品统计成本；
- 能统计人工处理节省。

### 7.3 Technology Notes

第一版技术重点：

- 批量导入优先，接口接入后置；
- 规则和统计优先，复杂模型后置；
- 人工确认优先，自动执行后置；
- 权限、审计、脱敏、用途登记必须前置。

### 7.4 Assumptions

- 客户愿意提供历史订单样本；
- 客户能确认数据使用目的；
- 历史数据能覆盖至少一个完整还款周期；
- 还款失败、复贷、对账至少有一个方向能被量化；
- 客户内部有业务负责人愿意推动试点。

## 8. Release

### V0: Historical Backtest Kit

目标：

- 用历史数据判断是否值得进入试点。

范围：

- 字段盘点；
- 数据质量检查；
- 订单事实层离线生成；
- 还款失败分布；
- 复贷候选回放；
- 对账差错样本；
- 初步价值报告。

不做：

- 生产自动化触达；
- 自动授信或评分；
- 实时接口；
- 客户端页面。

### V1: One-cycle Pilot

目标：

- 在一个真实还款周期里证明增量价值。

范围：

- 还款失败挽回队列；
- 策略动作记录；
- 合规复贷候选池；
- 差错订单处理队列；
- 增量价值报告；
- 客户复盘会。

不做：

- 全量自动化；
- 跨机构数据共享；
- 面向 C 端导流；
- 高风险外部信用标签。

### V2: Productized Workbench

目标：

- 从试点交付走向可重复销售。

范围：

- 多客户配置；
- 标准化字段模板；
- 权限和审计；
- 模块化报价；
- API 接入；
- 运营策略模板；
- 归因报表。
