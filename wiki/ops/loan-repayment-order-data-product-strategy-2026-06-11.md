# 贷款还款订单数据产品策略

## Trigger

用户要求把贷款还款场景作为独立细分领域，从头完成 PM 分析链路。本文负责产品策略，不重复总览和机会树。

## Strategy Summary

战略定位：

> 不卖原始数据，不做泛金融数据平台，而是把放款、还款和对账订单变成贷款机构的“还款运营增收工作台”。

第一阶段只解决三个能被订单数据闭环证明的问题：

1. 提升还款成功和失败后恢复；
2. 提升结清 / 稳定还款客户的合规复贷转化；
3. 降低渠道、对账、清算损耗。

## Product Strategy Canvas

### 1. Vision

成为贷款机构在还款生命周期里的经营基础设施。

客户不只是需要一张还款报表，而是需要回答：

- 哪些钱今天应该收回来；
- 哪些还款失败可以挽回；
- 哪些结清客户可以合规再经营；
- 哪些渠道和对账问题正在吞噬利润；
- 哪些行为信号提示贷后风险变化。

价值观：

- 数据用于客户授权范围内的经营改善；
- 优先帮助机构提升还款体验和资金效率；
- 不以出售个人金融明细作为商业模式；
- 不诱导过度借贷。

### 2. Market Segments

#### First Segment: 消费金融 / 小贷 / 助贷平台

JTBD：

- 在还款日附近提升扣款成功率；
- 对失败订单做快速恢复；
- 对结清客户做合规复贷运营；
- 用订单数据证明运营策略带来的增量。

为什么先做：

- 订单量大；
- 还款失败、复贷、对账痛点明显；
- 通常已有线上放款和还款订单；
- 对增收和降本结果更敏感。

#### Second Segment: 贷款科技服务商 / 贷后服务商

JTBD：

- 给多个贷款机构或资金方提供白标能力；
- 把技术链路包装成可收费产品；
- 用统一报表服务不同合作方。

为什么跟进：

- 可作为渠道和集成伙伴；
- 一次能力可复制到多个机构；
- 但需要处理多租户、权限、白标和归因。

#### Third Segment: 银行零售信贷部门

JTBD：

- 做资产质量监测；
- 降低对账和人工处理成本；
- 稳妥推进还款提醒和客户服务。

为什么不是第一优先：

- 合规、采购和系统集成周期更长；
- 对营销和自动化决策更谨慎；
- 早期适合做风险看板和对账报表，不适合先做复贷增长。

### 3. Relative Costs

成本定位：高信任、高价值的垂直运营基础设施，不做低价 BI 工具。

相对成本较高的原因：

- 需要接入敏感金融订单；
- 需要数据治理、权限、审计、脱敏；
- 需要业务归因和运营闭环；
- 需要与贷款核心、支付、清算、风控、CRM 系统集成。

收费逻辑：

- 用业务结果支撑溢价；
- 初期用服务化试点证明价值；
- 产品化后用 SaaS + 订单量 + 绩效分成组合收费。

### 4. Value Proposition

#### 消费金融 / 小贷 / 助贷平台

Before：

- 还款失败原因混乱；
- 客户结清后复贷触达粗放；
- 对账和渠道成本不透明；
- 运营策略效果无法归因。

How：

- 建立贷款订单事实层；
- 输出失败原因、重试策略、复贷候选、差错清单；
- 记录策略触达和结果；
- 提供恢复金额、复贷增量、对账节省的归因报表。

After：

- 更多应收款在宽限期内恢复；
- 结清客户被更合规地经营；
- 财务和运营减少手工对账；
- 管理层看到数据产品带来的收入和成本变化。

Alternatives：

- 内部 BI；
- 贷后系统；
- 催收系统；
- CRM；
- 支付渠道后台；
- 人工 Excel 对账。

#### 贷款科技服务商 / 贷后服务商

Before：

- 有客户和订单链路，但缺少可包装的产品模块；
- 每个贷款机构定制报表，交付成本高。

How：

- 提供白标工作台、API、指标体系和运营模板；
- 让服务商把还款恢复、复贷、对账能力作为增值服务售卖。

After：

- 服务商获得新增产品线；
- 多客户复用同一套能力；
- 以订单量或恢复金额形成持续收入。

### 5. Trade-offs

明确不做：

- 不做原始个人放款 / 还款数据交易；
- 不做跨机构个人信用评分网络；
- 不先做自动授信、自动定价、自动放款决策；
- 不先做 C 端贷款超市或导流入口；
- 不把催收强触达作为第一商业卖点；
- 不承诺绕过客户原有贷后系统，而是先做数据增值层和运营闭环。

这些取舍带来的聚焦：

- 降低合规和品牌风险；
- 更容易从现有支付 / 清算 / 贷款客户切入；
- 用订单数据闭环证明价值，而不是陷入泛平台叙事；
- 先卖可量化结果，再扩展能力。

### 6. Key Metrics

North Star Metric：

> Verified incremental repayment lifecycle value.

中文定义：

> 经客户确认、可归因的还款生命周期增量价值。

组成：

- 恢复金额增量；
- 复贷 / 续贷增量收益；
- 对账差错追回金额；
- 人工处理成本节省；
- 渠道成本节省。

OMTM：

> 2 个存量客户完成历史订单回测，1 个客户完成一个还款周期试点。

辅助指标：

- 还款失败后 72 小时恢复率；
- 自动 / 半自动分类覆盖率；
- 复贷候选转化率；
- 对账差错识别金额；
- 客户愿付价格或试点续约意向。

### 7. Growth

增长模式：Sales-led + Consulting-led pilot。

第一阶段获客：

- 从已有放款、还款、清算客户中筛选；
- 选择订单量高、对账痛、复贷压力高的客户；
- 用 6-12 个月历史订单做低成本回测；
- 用回测结果推动付费试点。

第二阶段扩张：

- 按客户内部部门扩张：运营、贷后、财务、风控、客服；
- 按模块扩张：还款恢复 -> 复贷运营 -> 对账清算 -> 风险监测；
- 按合作生态扩张：贷款科技服务商、资金方、渠道方。

单位经济：

- 试点期：项目费 + 恢复金额 / 差错追回分成；
- 产品期：SaaS 订阅 + 订单量阶梯价；
- 成熟期：API 调用 + 模块订阅 + 绩效分成。

### 8. Capabilities

必须自建：

- 贷款订单事实层；
- 还款失败原因归因；
- 还款生命周期分层；
- 对账差错识别；
- 策略效果归因；
- 权限、审计、脱敏和用途记录。

可合作：

- 客户原有贷款核心系统；
- 支付渠道和清算通道；
- CRM / 短信 / 企微等触达工具；
- 客服系统；
- 法务合规顾问。

组织能力：

- 金融支付和清算理解；
- 贷后运营理解；
- 数据分析和实验设计；
- B2B 试点交付；
- 合规边界管理。

### 9. Can't / Won't

竞争者不容易复制的地方：

- 订单链路接入深，连接放款、还款、渠道、清算、对账；
- 还款运营结果可回写，形成策略反馈；
- 客户一旦在账务和运营上依赖，迁移成本高；
- 不是单点模型，而是数据、运营、财务、合规的闭环。

我们不会用高风险方式换短期增长：

- 不卖个人明细；
- 不输出未经合规确认的外部信用标签；
- 不把复贷增长凌驾于客户保护和风险控制之上。

## Strategic Bets

1. 还款订单比静态客户资料更能反映贷后经营机会。
2. 贷款机构愿意为可归因的恢复金额、复贷增量和对账节省付费。
3. 最容易启动的不是大平台，而是历史订单回测和一轮还款周期试点。
4. 合规边界越清晰，越能进入高价值金融客户。

## Strategic Risks

- 如果客户数据质量太差，事实层建设会变成长期集成项目。
- 如果客户没有清晰授权和用途管理，复贷和风险模块推进会受阻。
- 如果只展示报表，不闭环到策略和收益，付费意愿会弱。
- 如果绩效分成无法归因，商业谈判会拖慢。

## Next Step

用产品发现文档里的机会树作为输入，推进一个最小商业验证包：

1. 历史订单回测；
2. 还款失败挽回方案；
3. 复贷候选池；
4. 对账差错清单；
5. 试点报价模型。
