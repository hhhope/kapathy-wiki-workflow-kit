# 详细设计文档 Skill

## Skill 说明

本 skill 帮助开发团队基于**五问框架**和**三轨迭代机制**生成结构化详设文档，实现"First One"原则：优先完成最小可交付集，再逐步补充细节。

AI 的角色是**辅助触发正确问题、枚举被遗漏的场景**，不替代开发者做技术判断。

---

## Step 0：收集必要 Context（强制，缺一不可）

> 在开始生成任何内容之前，必须先向用户收集以下信息。缺少必填项时，直接询问，不要跳过或假设。

### 必填 Context（缺少则无法启动）

| # | 信息项 | 说明 | 示例 |
|---|--------|------|------|
| 1 | **用户故事 / 需求描述** | P0 核心需求是什么，解决谁的什么问题 | "用户在 App 内完成支付时需要重复认证，希望打通认证流程" |
| 2 | **涉及的系统 / 服务** | 本次改动会触及哪些系统，包括上下游依赖 | "支付服务、认证中台、用户中心、通知服务" |
| 3 | **改动范围** | 新增功能 / 存量改造 / 接口变更 / 数据库变更 | "新增 3 个接口，修改 1 张表，不涉及前端" |
| 4 | **编写人 / 项目名** | 文档元信息 | "严鹏 / 支付认证打通项目" |

### 选填 Context（有则更好，没有可在文档中标注 TBD）

| # | 信息项 | 说明 |
|---|--------|------|
| 5 | **性能要求** | 响应时间、QPS、可用性要求 |
| 6 | **已知技术约束** | 语言版本、框架、不能用某个方案的原因 |
| 7 | **外部依赖情况** | 第三方服务、内部其他团队的系统 |
| 8 | **发布时间节点** | 影响迭代计划排期 |
| 9 | **安全 / 合规要求** | 数据加密、审计日志、权限模型 |

### Context 收集话术

如果用户没有主动提供，按以下方式询问：

```
在开始写详设之前，我需要了解几个关键信息：

1. 这次需求的核心是什么？解决谁的什么问题？（一两句话即可）
2. 涉及哪些系统或服务？（包括上下游依赖）
3. 改动范围大概是什么？（新增接口/改表/存量改造等）
4. 你的名字和项目名是？

有了这些我就能开始帮你生成结构化的详设文档。
```

## Step 1：生成文档框架并填充已知信息

收集完必要 context 后：

1. 基于 `references/template.md` 加载完整文档结构
2. 将用户提供的 context 填入对应章节
3. 对于缺失信息，标注 `[TBD - 需补充]`，不要捏造内容
4. 在文档顶部生成**Context 确认清单**，让用户二次确认信息是否准确

### 填充规则

- **核心矛盾（1.1）**：从用户故事中提炼，如用户已给出一句话核心矛盾则直接使用，否则根据需求描述自动生成并请用户确认
- **涉及系统 → 外部依赖（1.4）**：将用户提供的系统列表映射到依赖表
- **改动范围 → 功能边界（1.4）+ 接口清单（Q3）**：根据改动范围预填边界和接口框架
- **ADR（Q2）**：如果用户未提供技术决策信息，生成 ADR 占位并提示用户填写

---

## Step 2：五问框架引导

文档框架生成后，按以下顺序引导用户逐步回答五个问题。**不要一次性抛出所有问题**，每个问题确认后再进入下一个。

### Q1 引导话术
```
框架已生成。先来确认问题边界：

从技术视角看，这次最大的挑战是什么？
（比如：一致性问题、第三方依赖稳定性、并发场景、数据迁移风险…）

另外，这次方案有意识地不解决哪些问题？
```

### Q2 引导话术
```
接下来记录关键技术决策（ADR）。

你在这次设计中有没有做了一些「换个人可能会做不同选择」的技术决定？
（比如：选了 A 方案而不是 B、用了某个中间件、选择了最终一致性而非强一致…）

每个决策我会帮你生成 ADR 格式，你来判断备选方案的取舍理由。
```

> **AI 辅助**：在用户描述决策背景后，生成备选方案对比表，供用户选择和修改，不要直接给出推荐结论。

### Q3 引导话术
```
现在来设计主流程。

能描述一下核心链路的步骤吗？（谁调谁，传什么，返回什么）

我会帮你生成时序图框架，你来补充细节。
注意：时序图里需要包含至少一条异常分支，以及每个外部调用的超时时间。
```

> **AI 辅助**：根据用户描述的系统和流程，生成 Mermaid 时序图草稿，让用户修改。

### Q4 引导话术
```
主流程设计好了，现在来想「出错了怎么办」——这是最容易被跳过但最重要的部分。

你在 Q3 里列了这些外部依赖：[列出依赖列表]

逐个问你：
- [依赖A] 如果超时/不可用，你的服务怎么处理？降级还是直接失败？
- [依赖B] 同样的问题…

另外，有没有写操作需要保证幂等性的？
```

> **AI 辅助**：对每个外部依赖，枚举可能的故障场景（超时、返回异常、数据错误），帮用户想全，但降级策略由用户决定。

### Q5 引导话术
```
最后，怎么证明这个设计是对的？

请说出你觉得最可能出错的 3 个场景（不能少于 3 个）。
想不出来说明设计还有盲区，可以从这几个方向想：
- 并发场景
- 外部依赖故障时
- 边界数据（空值、超大值、重复请求）
- 状态机流转异常
```

> **AI 辅助**：根据时序图和系统列表，推演可能遗漏的出错场景，供用户参考和补充。

---

## Step 3：最小交付集检查

文档生成完成后，执行门禁检查，输出如下格式：

```
## 最小交付集检查

### 需求定义阶段
- [x] 1.1 核心矛盾（一句话）✅
- [x] 1.3 验收标准（P0 功能点）✅  
- [x] 1.4 功能边界（包含 + 不包含）✅

### 设计阶段
- [x] Q1 问题边界 ✅
- [x] Q2 至少 1 条 ADR ✅
- [x] Q3 主流程时序图（含异常分支）✅
- [ ] Q4 外部依赖降级策略 ⚠️ [依赖B] 的降级策略未填写
- [x] Q5 3 个出错场景 ✅

### 结论
设计阶段最小交付集未完成，需补充 Q4 中 [依赖B] 的降级策略后方可进入迭代阶段。
```

---

## Step 4：输出文档

1. 生成完整 Markdown 文档
2. 文档命名格式：`详设_[项目名]_[编写人]_[日期].md`
3. 保存到 `/mnt/user-data/outputs/` 目录
4. 使用 `present_files` 工具提供给用户下载

---

## AI 辅助边界说明

在引导过程中，始终遵守以下边界：

| 阶段 | AI 可以做 | AI 不替代 |
|------|----------|----------|
| 核心矛盾 | 根据需求描述生成候选句，让用户确认 | 最终定义 |
| ADR | 生成备选方案对比，枚举各方案优劣 | 技术选型决策 |
| 时序图 | 生成草稿，补全可能遗漏的异常分支 | 业务流程定义 |
| 降级策略 | 枚举每个依赖的故障场景 | 降级方案选择 |
| 出错场景 | 根据系统推演可能遗漏的场景 | 验收标准制定 |
| 代码评审 | 对比实现与设计文档的一致性 | 架构合理性判断 |
