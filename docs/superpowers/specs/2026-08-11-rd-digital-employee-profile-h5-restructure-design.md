# 研发数字员工画像 H5 叙事重构设计

## 1. 重构目标

把现有 H5 从“概念页加案例卡”的表达，重构为一条可验证的研究叙事：

`企业 AI 全链路 → 企业采用现状 → Agent 解决的问题 → 我们的研发数字员工画像 → 上岗与考核 → 数字员工的一天`

重构不是增加章节，而是改变读者理解顺序。企业案例不再充当开场，而是在统一架构和评级尺下成为证据。

## 2. Article Intent Contract

| 字段 | 约定 |
|---|---|
| 读者 | 研发管理者、技术负责人、产品经理和数字员工试点负责人 |
| 读者任务 | 判断企业要具备什么条件才能使用数字员工，并据此选择研发数字员工试点 |
| 主线 | 数字员工不是更聪明的聊天机器人，而是建立在企业知识、系统、权限、记忆和岗位治理之上的岗位级 AI |
| 非目标 | 不做企业排行榜，不把采用率等同于成熟度，不讨论人员替代，不授予生产权限 |
| 用户拥有的判断 | 采用 L1—L6；先讲参考架构图，再讲企业调研，再解释 Agent，最后讲我们的研发数字员工 |
| Agent 可执行范围 | 重排内容、重画信息图、压缩重复概念、映射公开证据、完成本地 H5 与验证 |

## 4. 选择的结构方案

采用六个内容页的“行业 → 原理 → 我们”方案。首屏只承担标题、核心结论和阅读地图，不再放一张与正文重复的总览长图。

### 页面 01：企业 AI 全链路架构

**读者问题：**一个 AI 为什么能从聊天工具变成公司的数字员工？

主体采用七层纵向堆叠的一图流：

1. 原始资料层：业务系统数据、文档表格、沟通记录和经验。
2. 系统连接层：接口、数据库、文件同步、消息通道和业务流程。
3. 权威知识层：权威来源、版本有效期、冲突处理、责任人与下架机制。
4. 企业记忆层：会话记忆、岗位记忆、企业记忆和经验沉淀。
5. 检索与上下文层：理解问题、定位范围、权限过滤、组装上下文和出处标注。
6. 岗位能力层：读、写、建、审、回写，并配套责任、数据、动作和验收边界。
7. AI 员工层：销售作战、客服、数据分析、知识管家、审批协办等岗位单元。

每层只回答三件事：本层提供什么、依赖什么、缺少它会退化为什么。

右侧设置“通用 AI 与数字员工”八项对照：企业知识、系统连接、权限、记忆、持续运行、动作、过程可查和结果评价。

底部设置九步上岗链路：

`选岗位 → 盘点资料 → 连接与治理 → 设权限 → 配岗位能力 → 真实数据试跑 → 人工审核 → 影子运行 → 复制到下一岗位`

结论固定为：**数字员工不是更聪明的聊天机器人，而是建立在企业知识中枢之上的岗位级 AI。**

### 页面 02：企业采用现状与 L1—L6

**读者问题：**哪些企业真的在使用数字员工，它们分别走到了哪里？

页面主体改为研究表格，不再使用三张大案例卡。表格字段：

| 字段 | 说明 |
|---|---|
| 企业 | 企业名称 |
| 行业 | 互联网、支付、金融、AI 软件、工业等 |
| 数字员工实践 | 实际岗位或流程 |
| 公开采用数据 | 有明确分母、工作量或覆盖面的数字 |
| 观测能力 | 对应七层架构的已验证能力 |
| 推断等级 | L1—L6 的最高保守等级 |
| 证据强度 | 高、中或候选，并说明缺口 |

首版优先展示 8—10 家有代表性企业，至少包括腾讯、Block、Salesforce、IBM、工商银行和兴业银行。腾讯、Block、IBM 作为三条强证据行高亮；如果最终核验显示其他企业证据更强，可替换高亮对象，但不得只因品牌知名度替换。

表格下方绘制 L1—L6 横轴，并把企业以标签放在对应等级：

- L1 工具助手
- L2 知识助手
- L3 任务型 Agent
- L4 岗位数字员工
- L5 数字员工网络
- L6 AI 原生企业

必须同时注明：采用率与 L 等级是两条轴；全员使用不等于 L5；评级是公开证据下的保守推断，不是企业自评。

### 页面 03：Agent 解决的问题

**读者问题：**企业为什么不能只部署一个通用聊天 AI？

上半部分采用“企业问题 → Agent 能力”的因果图：

`资料分散 → 检索与上下文`

`知识不可信 → 权威知识`

`系统彼此割裂 → 工具连接`

`流程依赖人盯 → Orchestration`

`任务容易中断 → 状态与恢复`

`动作风险不清 → 权限与 Gate`

`结果无人负责 → 岗位身份与考核`

下半部分使用通用 AI、Agent、数字员工三列对照：通用 AI 主要回答问题；Agent 围绕目标执行受控任务；数字员工进入岗位、权限、责任和考核体系。

本页同时澄清：

- SOP 规定通常应该怎么做。
- Orchestration 根据当前状态决定谁在何时调用什么能力。
- 状态机保存任务状态和允许的跳转，是 Orchestration 的实现机制之一，不等于 Orchestration。

### 页面 04：我们的研发数字员工一图流

**读者问题：**研发数字员工究竟由什么组成？

整页采用“岗位核心＋六个环”的画像总图：

- 中心：岗位使命、服务对象和交付结果。
- 身份与权限：身份卡、责任主体、最小权限、拒绝与升级边界。
- 知识与记忆：代码仓、架构决策、历史缺陷、运行数据和岗位记忆。
- SOP 与 Orchestration：标准方法、动态编排、状态、恢复和 Gate。
- 工具与行动：代码、测试、工单、文档、环境和协作工具。
- 行为与能力：证据优先、克制变更、可恢复、可协作、可审计及十维能力。
- 评测与进化：结果、质量、成本、可靠性、反馈和版本迭代。

本页承载画像总定义，不再把身份卡、行为特征和能力结构拆成多张没有关系的卡片。

### 页面 05：上岗、定级、使用与考核

**读者问题：**如何判断一个研发 Agent 可以作为数字员工上岗？

采用四段式岗位档案：

1. 身份卡：名称、岗位使命、服务对象、责任人、默认自治等级和成功标准。
2. 十维能力雷达：只表达相对能力重点；旁边同时给出可观察证据，避免把主观评分当成事实。
3. A0—A4 自治等级：V1.0 聚焦 A2—A3，风险升高时动态降级。
4. 场景与考核：用任务适配矩阵对应交付、质量、人效、可靠性、经济性、学习和治理指标。

需要明确区分：L1—L6 衡量企业落地成熟度；A0—A4 衡量单个研发数字员工的自治边界。

### 页面 06：研发数字员工的一天

**读者问题：**前面的架构、能力和治理如何在一个真实任务中共同工作？

使用一个有明确复现步骤、测试环境和验收标准的后端缺陷修复任务，以横向时间轴回放：

`接单 → 准入检查 → 理解上下文 → 规划 → 实现 → 测试验证 → 人类 Gate → 交付候选变更 → 复盘`

时间轴同时展示四条泳道：数字员工、Orchestration/状态、企业系统、人类主管。每个节点标注调用的 SOP、权限、证据、失败恢复方式和考核信号。

任务终点是“可评审候选变更”，不自动合并或发布生产。

## 6. 视觉系统

- 白色底，深蓝正文，蓝、青、橙、紫对应七层和不同信息角色。
- 风格接近研究型一图流，不采用营销落地页的大留白、大数字卡和无意义图标。
- 每页必须有一个可截图传播的完整视觉主体；正文只负责解释判断和证据边界。
- 表格行高、字号和颜色按证据强弱建立层级，不用品牌 Logo 主导视觉。
- 桌面端最大内容宽度扩大到适合高密度图表的范围；移动端表格和横轴采用有提示的局部横向滚动，页面本身不得横向溢出。

## 7. 数据与证据规则

- 企业数据只使用可直达的企业官方材料、年报、投资者材料或政府案例。
- 每个企业至少提供实践、一个公开信号、推断等级、证据强度和缺口。
- 采用率数字保留原始分母和对象，不把“程序员采用率”改写成“全员采用率”。
- 单一高阶试点不代表整个集团达到该等级。
- 多个 Agent 同时存在不等于 L5；L5 需要分工、交接、统一权限和统一监控的公开证据。
- 当前没有充分证据时，不展示 L6 企业案例。

## 8. 交互与降级

- 保留章节导航和阅读进度，但导航语言改为“行业全景 / 我们的画像”。
- 表格支持行业和 L 等级的轻量筛选；无 JavaScript 时完整表格仍可阅读。
- 一图流中的层级和节点可聚焦查看解释，不依赖悬停才能获得关键信息。
- `prefers-reduced-motion` 下关闭位移动画。
- 所有横向滚动容器提供键盘焦点和滚动提示。

## 9. 验收标准

### 内容验收

- 阅读前三页即可回答：数字员工需要什么企业底座、行业走到哪里、Agent 解决什么问题。
- 阅读后三页即可回答：我们的研发数字员工是什么、如何上岗考核、一天如何运行。
- L1—L6 与 A0—A4 不混用。
- SOP、Orchestration 和状态机的关系前后一致。

### 视觉验收

- 1440×1000 下页面 01 七层图无需缩放即可理解主线。
- 390×844 下页面无整体横向溢出；表格和横轴只在自身容器内滚动。
- 六页各自存在清晰主视觉，且没有重新退化成同构卡片堆叠。
- 公司表格可在十秒内找到企业、数据、等级和证据缺口。

### 技术验收

- 本地 CSS、JavaScript 和图片资源无缺失。
- 无 JavaScript 时正文顺序完整。
- 控制台无错误，章节导航、表格筛选和展开说明可用。
- 对桌面端和移动端进行 fresh visual QA 后才能声称视觉完成。

## 10. 交付边界

- 只修改仓库内 H5、样式、脚本和必要的本地视觉资产。
- 不发布、不部署、不同步飞书。
- 原有研究和旧一图流作为来源保留，不把旧截图继续当成新页面 01 的主体。
