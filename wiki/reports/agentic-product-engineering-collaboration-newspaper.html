AI Agent 时代产研协作观察报

262 个 source entries 之后，行业真正争论的不是工具，而是谁定义目标、谁承担判断、谁审查结果、谁拥有作业系统。

头版判断

产研协作正在从人力流水线，变成人机作业系统。

Agent 不是把工程师变快的插件。它把 ticket、spec、PR、CI、eval、wiki 变成可执行对象。人不再只负责把上下文传给下一个人，而要负责目标、边界、判断和后果。

旧问题：怎么让人更快交付？

产品、设计、工程、测试按顺序接力。上下文靠会议和文档搬运，质量靠末端验收兜底。

新问题：怎么让系统可执行、可审查、可沉淀？

人定义目标和判断边界，agent 执行和自证，结果进入 PR、review packet、eval、wiki、rules。

02 传统协作链

传统协作不是没有中间层，而是中间层主要由人、会议、文档、表格和局部脚本承担。

03 AI 时代执行单元

找上下文、拆任务、生成初稿、跑验证、整理证据，被拆成可排队、可审查、可复用的执行单元。

04 左端：执行自动化公司

共同方向是把 Agent 放进真实工作入口，而不是只停留在聊天窗口。

  • OpenAI / Anthropic
  • GitHub / Atlassian / JetBrains
  • Cursor / Sourcegraph / Replit

05 警告：别讲成中间人消失

更稳妥的说法是：转述型中间劳动被压缩，判断型中间责任被抬高。

06 右端：组织治理讨论

当执行层变快，稀缺项从“谁来做”转向“谁允许、谁检查、谁承担、谁沉淀”。

  • Microsoft / IBM / Deloitte / Gartner
  • DORA / Stack Overflow / GitLab / METR

07 高风险样本提示

Block、Stripe、Ramp、PayPal、AWS 这类 payment、infra、security、customer data 场景，要求自动化和治理同桌讨论。

这里的重点不是给公司排位，而是说明为什么“自动化端”和“治理端”会同时变重要。

章节 takeaway：AI 时代公司不是简单变扁，而是两端变重，中间协作层从传话链变成作业桥。

01 旧中间层

PM 转译需求，TL 拆任务，QA 兜质量，运营追状态。它不是不存在，而是分散在人的记忆、经验和同步机制里。

02 变化本质

Agent 新增的不是“中间层”，而是把部分中间工作变成系统对象：可触发、可排队、可调用工具、可产出证据。

03 四个新属性

可调用
可审查
可回放

再加上可沉淀：失败写回 rules、tests、wiki、skill。

04 旧流水线

产品 -> 设计 -> 工程 -> 测试 -> 发布。问题常在末端暴露，返工靠再次开会和再次解释。

产品->设计->工程->测试

05 新作业面

人定义目标、边界、非目标、验收标准；Agent 承担检索、生成、实现、验证、证据打包等可执行部分。

06 警告：别把判断外包

Agent 可以执行中间工作，但不能替公司决定目标、取舍、责任和风险承受。没有 owner 的 Agent queue，只会把混乱放大。

07 落地观察

  • cycle time
  • 返工率 / review reject
  • 缺陷外逃 / 上下文补问次数
  • 失败是否写回系统
章节 takeaway：Agent 没有发明中间层，它重写了中间层的承载方式。

01 入口：人定目标

循环从人开始。目标不清，后面的执行越快越危险。

02 上下文：可执行包

Agent 需要的不是一句口令，而是背景、边界、示例、反例、数据入口、测试方法和已知风险。

03 执行：Agent Queue

它应当像任务队列，而不是像聊天窗口：找资料、拆步骤、改代码、跑检查、整理证据。

04 审查：Review Packet

输出不能只是答案。它要带上变更点、依据、验证结果、失败项、风险和待人判断问题。

05 回放与沉淀

输入、工具调用、关键判断、测试结果和人工审查意见留下痕迹；失败写回新测试、新规则、新示例和新知识页。

06 警告：闭环不是全自动

闭环不是 Agent 自己批准自己。高风险节点必须有人审、可追责、可回滚。

中间执行层从“人靠经验转述”变成“系统可调用的工作循环”；人的位置上移到目标、边界、审查和责任。

章节 takeaway：闭环不是全自动，而是每次执行都留下证据、审查和写回。

现有公司的人该怎么做

role-by-role operating change
CEO / GM

别把 AI 当采购项目

  • 选一个真业务瓶颈做 30-60 天试点。
  • 明确质量、风险、成本和责任边界。
  • 用流程结果考核，不用“用了多少 AI”考核。
Product / PM

从需求转述者变成判断 owner

  • 写清目标、非目标、用户场景和验收标准。
  • 把 ticket/spec/wiki 做成 agent 可执行上下文。
  • 保留取舍权，不能把产品判断外包给模型。
Designer / Research

把体验判断变成可测试样本

  • 沉淀用户语境、反例、边界场景和体验红线。
  • 用原型和 review packet 审 agent 产物。
  • 把“像不像人话”变成示例和检查项。
Engineer / TL

从写代码扩展到管理执行系统

  • 设计工具权限、上下文入口、测试和回滚。
  • 审查 agent 输出是否真的满足 spec。
  • 把失败写回 eval、lint、guardrail、skill。
QA / Data / Ops

把反复出错的地方变成 eval

  • 从末端兜底转向前置风险样本库。
  • 把缺陷、异常、客诉、合规点结构化。
  • 用可复跑检查证明 agent 没有只会演示。
Manager / HR

重写岗位边界和成长路径

  • 区分可自动化执行和必须人类判断的工作。
  • 训练员工写上下文、审证据、管风险。
  • 调整绩效：看结果质量、系统沉淀和协作吞吐。

我们应该怎么做

local operating principles

三条原则

  • 目标人定。业务目标、用户价值、优先级、风险承受度不能交给 agent。
  • 过程可委托。检索、整理、生成、实现、验证、回放可以交给 agent。
  • 结果可审计。所有输出必须进入 PR、review packet、eval、wiki、日志这类可追踪对象。

第一条试点链路

  • 从会议材料、文章或需求进入。
  • 沉淀成 spec / wiki / issue。
  • agent 产出草稿、代码改动或 review packet。
  • 人审查判断，失败写回规则、测试、skill、wiki。
