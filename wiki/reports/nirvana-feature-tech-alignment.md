# 涅槃项目功能-技术对齐底表

## 一、使用说明

这份底表不是风险页，也不是汇报页，而是项目管理工作底表，目标是回答四个问题：

1. 产品现在希望交付哪些功能
2. 技术现在真实承接到哪里
3. 哪些点已经有排期但边界还没冻结
4. 哪些点还不能对客承诺

建议后续持续维护下面五列：

- 产品功能
- 对客优先级
- 当前技术状态
- 待确认点
- 管理动作

管理动作统一只用三类：

- `纳入本期承诺`
- `内部推进，不对客承诺`
- `冻结后再排期`

## 二、当前总判断

### 1. 当前项目不是“没有排期”，而是存在三层错位

- 产品需求范围已经大于当前技术主承接范围
- 技术部分功能虽然已有排期，但产品边界还没冻结
- 部分对客敏感能力已经写进需求，但技术还没有完整成包承接

### 2. 当前最需要管理的不是单点风险，而是三类边界

- 哪些功能现在可以对客承诺
- 哪些功能只能内部推进
- 哪些功能必须先完成产品技术确认后才能进入稳定排期

### 3. 当前整体状态判断

| 维度 | 当前判断 |
| --- | --- |
| 主链路交付 | 一步支付、网关、账户基础能力推进较明确 |
| 周边运营能力 | BM、回单、对账、退款治理承接不足 |
| 分账耦合能力 | 讨论多、边界未稳、最容易影响项目整体收口 |
| 配置迁移与外围改造 | 有推进，但被主链路持续挤压 |
| 对客口径稳定性 | 当前不宜把完整需求包直接等价为已承接交付包 |

## 三、功能-技术-待确认主表

## 3.1 协议支付主链路

| 产品功能 | 对客优先级 | 当前技术状态 | 待确认点 | 管理动作 |
| --- | --- | --- | --- | --- |
| 一步支付 | 高 | 已明确承接，已有明显进度，周报持续跟踪 | 当前是“开发完成”还是“测试通过可交付”，口径需统一 | 纳入本期承诺 |
| 预支付 | 高 | 技术有排期 | 是否本期必交，还是补齐型能力 | 内部推进，不对客承诺 |
| 确认支付 | 高 | 技术有排期 | 是否必须与预支付一起作为完整闭环交付 | 内部推进，不对客承诺 |
| 支付结果通知 | 高 | 技术已承接，已有测试推进 | 通知字段、失败重试、商户验收口径是否冻结 | 纳入本期承诺 |
| 通知清算 | 高 | 技术已承接 | 清算口径是否最终确认 | 内部推进，不对客承诺 |
| 支付订单补单 | 中 | 技术承接中，但周报显示资源受挤压 | 补单是否仍在本期范围 | 冻结后再排期 |
| 补发清算 | 中 | 有排期，但周报显示暂停或受影响 | 是否本期必须 | 冻结后再排期 |
| 支付订单查询 | 中 | 有排期 | 查询字段是否满足产品和对客场景 | 内部推进，不对客承诺 |

### 当前判断

- 主链路不是没做，而是“前半段更清晰，末端闭环还不稳定”
- 对客如果要说“协议支付可交付”，必须拆开说，不宜整体打包

| 绑卡流水查询 | 中 | 需求明确，技术识别到，但未看到稳定闭环 | 返回历史状态还是当前状态，产品口径需锁定 | 冻结后再排期 |
| 协议状态查询 | 中 | 需求有，但承接不够清晰 | 与绑卡流水查询是否分开交付 | 冻结后再排期 |

- 绑卡能力已经进入需求正式范围
- 但技术当前主力仍在支付主链路，绑卡更多是后排项
- 不适合现在直接对客承诺完整绑卡包

## 四、待确认清单

## 4.1 必须由产品和技术一起冻结的事项

| 主题 | 当前问题 | 建议结论动作 |
| --- | --- | --- |
| 本期协议支付范围 | 只含基础支付闭环，还是包含绑卡、退款、BM、分账前收单、新代收兼容 | 先冻结本期范围，再更新承诺口径 |
| 协议支付用于分账 | 算 M2 还是 M3 | 必须明确归属，否则持续吃主链路资源 |
| 分账退款 | 是否按原方案推进，还是按重评结果重排 | 先冻结方案，再给排期 |
| 退款包范围 | 是否包含 BM 发起退款、退款审核、批量退款、退款查询、退款手续费展示 | 形成一个统一退款交付边界 |
| BM 范围 | 是否包含交易查询、详情、对账、回单、退款入口 | 单独形成 BM 交付包 |
| 对账 / 回单 | 是只保 API 不变，还是 BM 侧也必须完整交付 | 明确“API 范围”和“运营范围” |
| 撞库 | 是否进入本期 | 不明确则先不承诺 |
| 失败计费 | 是否进入本期，归哪个系统负责 | 明确 owner 和范围 |
| 签约支付 / 新代收 / 路由重发 | 是本期兼容范围，还是后续预留 | 避免技术过早拆散主线 |
| 异步通知整理 | 是参数补齐，还是统一口径改造 | 明确工作量级别 |
| AD 菜单迁移 | 是本期必须项，还是继续挂起 | 影响对客控台体验 |

## 五、对客口径建议

## 5.1 当前可以相对稳定对客表达的

- 协议支付主链路正在推进，核心支付能力已有明显进展
- 网关、账户基础能力已进入联调或测试阶段
- 项目当前主推进带明确围绕支付主链路、网关、账户收口展开

## 5.2 当前不宜直接整体承诺的

- 完整退款能力包
- 完整 BM 运营能力包
- 协议支付与分账组合能力包
- 撞库、失败计费、新代收、签约支付等扩展能力
- AD、配置迁移、通知口径统一这类外围收口项

## 5.3 当前对内必须持续追的

- 本期范围冻结
- 分账退款评审结论
- 网关 NACOS 接入后的回归安排
- 账户与协议支付联调窗口
- 补单 / 补发清算是否仍保留在本期
- BM 和退款治理是否进入本期正式承接

## 六、管理视图建议

后续如果转 HTML，建议首页只做三块：

1. `本期可承诺`
2. `内部推进中`
3. `待冻结后排期`

并且每块都按模块展示：

- 协议支付主链路
- 绑卡
- 退款
- BM
- 分账耦合
- 账户清算
- 网关与迁移

这样后续不管是你自己管项目，还是对上同步，都不会重新回到“纯风险说明”的视角，而是直接落到交付管理视角。

## 七、当前一句话结论

当前项目真正的 gap 不是“产品提了、技术没做”，而是：

- 产品功能包已经大于技术当前稳定承接包
- 技术部分排期已经先行，但边界还没冻结
- 如果不先把本期范围、BM 范围、退款范围、分账耦合范围冻结，对客口径和交付口径会持续错位
