## 一句话定位

Account Wiki 的运行态不是“材料放进哪个目录”，而是一个协作系统：Wiki 保存结构，skills 决定路由，agent 执行整理和改写，reviewer / gate 负责阻止漂移，回放和回读把结果写成可检查证据。

## 这页适合谁看

| 如果你现在想知道 | 先看这里的什么 | 看完能判断什么 |
|---|---|---|
| 新材料来了怎么处理 | 一份材料的运行链路 | 它应该成为来源、学习、操作记录、报告，还是一次性回答 |
| Wiki 目录为什么这样分 | Wiki 的结构分工 | 哪类内容应该落在哪一层 |

| 为什么不能直接写飞书 | 发布前门禁 | 什么时候必须先冻结、回放、重写 |

## 01 运行态先从输入分类开始

一份输入进入后，第一步不是写正文，而是判断它是什么。

| 输入类型           | 典型来源            | 默认路由                            | 不应该直接做什么 |
| -------------- | --------------- | ------------------------------- | -------- |
| 原始材料           | 飞书文档、会议纪要、附件、图片 | `wiki/sources`                  | 不直接改写成结论 |
| 行动 / 分歧 / 方法校准 | 会话、复盘、推进记录      | `wiki/ops`                      | 不伪装成稳定知识 |
| 可复用专题知识        | 多次出现的判断、结构、案例   | `wiki/domains` / `wiki/reports` | 不丢掉来源链接  |
| 对外表达           | 飞书审核稿、H5、报告页    | `wiki/reports` + gate review    | 不跳过质量门禁  |
| 稳定治理决策         | 长期规则、边界、生命周期决策  | `wiki/adr` / `openspec`         | 不靠聊天口头生效 |

这个分类决定后面的技能链。分类错了，后面写得再漂亮也会漂移。

## 02 Wiki 结构负责承接不同资产

Account Wiki 至少有六个运行层。

| 层 | 本地位置 | 承接什么 | 运行态责任 |
|---|---|---|---|
| 来源层 | `wiki/sources` | 上游材料、链接、会议、文章 | 保留事实来源和上下文 |
| 操作层 | `wiki/ops` | 探索、复盘、gate review、运行记录 | 保留过程、判断、失败和证据 |
| 专题层 | `wiki/domains` | 稳定主题知识 | 把分散经验组织成可复用专题 |
| 报告层 | `wiki/reports` | 读者要看的文章、汇报稿、视觉稿 | 把内部知识改写成可读输出 |
| 决策层 | `wiki/adr` | 稳定架构和治理决策 | 记录为什么这样做、不做什么 |
| 变更层 | `openspec` | workflow / skill / repo 行为变化 | 承接 proposal、design、tasks、evaluation |

这也是为什么运行态不能只画一条“输入 -> 输出”的直线。输入会按价值和风险分流到不同层，后续还可能从报告层、操作层再写回来源、专题或 OpenSpec。

## 03 Skills 负责把输入送进正确工作流

Skills 不是内容资产本身，而是运行时的路由和工作方式。

| Skill / 角色 | 触发场景 | 运行时作用 | 不能替代什么 |
|---|---|---|---|
| `learning-capture` | 外部文章、repo、README、参考样例 | 判断是否值得学习，记录可复用点和输出用途 | 不自动晋升为规则 |
| `weixin-reader` | 微信文章读取 | 抓取标题、作者、正文等原始信息 | 不判断学什么、落哪里 |
| `material-collaboration-defaults` | 材料、附件、报告源 | 先产出可读来源页，再看是否需要 ops 输出 | 不直接发布对外稿 |
| `meeting-note-output` | 会议纪要、转写、妙记 | 生成审核版会议纪要和待确认项 | 不带疑点直接同步最终版 |
| `public-report-quality-gate` | 飞书审核稿、H5、分享稿、报告 | 先做参考结构、split、voice、visual、publish gate | 不替代 Feishu 写入或最终验证 |
| `infographic-onepager` | 一图流、章节配图、横版教学卡 | 按信息密度选择竖版一图流或横版章节卡 | 不把所有图都做成六段海报 |
| `verify-before-claiming` | 要说完成、同步、干净、可发布 | 先用当前命令或回读证据确认 | 不凭记忆下结论 |
| `openspec-*` | 工作流、skill、repo 行为变化 | 用 proposal/design/tasks/evaluation 承接变更 | 不允许在完成 change 后继续偷改 |

运行态的关键不是 skill 越多越好，而是每个 skill 只拥有自己的边界。边界清楚，系统才不会把学习、写稿、发布、治理混成一条失控链路。

## 04 Agent 和 reviewer 负责不同阶段

默认 agent 负责读取上下文、执行本地写作、更新 wiki、跑验证。复杂对外材料还需要 reviewer 角色介入，但 reviewer 不是自动生成另一个 agent。

| 角色 | 什么时候进入 | 做什么 | 输出 |
|---|---|---|---|
| 默认 agent | 每次任务执行 | 读取 repo 约束、选择技能、编辑本地稿、记录证据 | wiki 页面、OpenSpec 任务、验证结果 |
| `public-report-reviewer` | 多页、参考结构、公开目标、失败历史同时出现时 | 先检查命题、模板、学习映射、硬门禁和同步 readiness | reviewer 结论或 `INVALID` |
| 人 | 选源、定命题、确认发布、处理分歧 | 判断什么值得做、什么不能发布、什么只是候选 | 方向、确认、拒绝或新约束 |

这次 Account Wiki 返工就是一个典型例子：默认 agent 可以修本地稿和证据；但一旦要说“可同步飞书”或“可对外 review”，就必须回到 public report gate 和 reviewer routing。

## 05 一份材料的真实流转

下面是一份输入从进入到复用的完整运行链。

```text
输入进入
  -> 保留来源：wiki/sources 或外部链接记录
  -> 判断类型：学习 / 材料 / 会议 / 对外稿 / 治理变更
  -> 选择 skill：learning、material、meeting、public-report、openspec
  -> 生成过程物：wiki/ops、wiki/reports、evaluation、gate review
  -> 通过门禁：参考结构、split、voice、visual、publish、replay
  -> 形成输出：本地审核稿、章节配图、报告页、候选规则
  -> 写回 Wiki：来源、边界、失败、通过证据、下一步
```

关键点是最后一步：好的运行态不会把成果留在聊天里。一次失败要写回为什么失败，一次通过要写回凭什么通过，一次学习要写回用在输出的哪里。

## 06 对外稿的运行链更严格

对外稿不能从“有内容”直接跳到“同步飞书”。

| 阶段 | 必做动作 | 失败时怎么处理 |
|---|---|---|
| 命题 | 先确定读者、问题、结论、非目标 | 命题不清就停止写稿 |
| 参考结构 | 读参考入口和具体子页，确认页面分工、视觉逻辑、写作标准 | 参考没读全，gate 失败 |
| 拆分 | 判断是一页、五篇、还是章节配图 | 多个读者任务塞一页，gate 失败 |
| 视觉 | 判断是一图流、横版章节卡、表格还是 HTML/SVG | 参考有关键图而本地无图，不能降级成小风险 |
| 审核 | 记录 scorecard、`INVALID` 或通过原因 | 硬门禁失败就冻结，不继续润色 |
| 回读 | Feishu 或外部目标更新后读回标题、开头、log id | 不能只凭命令成功说完成 |

所以这套系统不是为了多加流程，而是为了让“什么时候不能继续”变得可见。

## 07 运行态的边界

| 不能说 | 更准确的说法 |
|---|---|
| Wiki 会自动把材料变成团队共识 | Wiki 保存证据和结构，共识仍需要人确认 |
| 有 skill 就一定会稳定触发 | 触发行为需要 pressure scenario 和 replay evidence |
| 有 reviewer 就能替代用户判断 | reviewer 只能检查结构和风险，不能决定业务取舍 |
| 有图就算视觉 gate 通过 | 图必须承载结构、流程、对比或判断 |
| Feishu 更新成功就是发布完成 | 还需要回读验证和发布状态确认 |

## 收尾判断

Account Wiki 的运行态可以概括成一句话：

> 来源进入 Wiki，skills 决定路线，agent 执行整理，gate 拦住漂移，replay 证明行为真的发生，最后把可复用结果写回结构。

如果少了写回和验证，它只是一次对话。如果少了来源和边界，它就会变成漂亮但不可信的文档。
