# 多渠道收款商户法人短信认证需求分析

## 结论

本需求的核心是：多渠道收款产品开通前增加法人短信认证，法人未完成短验时，新会员链路停在提交 118 流程前，老前置链路停在发起 83 流程前；法人完成短验后，产品开通流程继续。

当前需求骨架已经可进入人工评审；但详细设计、API、表结构、状态机和开发拆解仍不能开始，除非补齐或明确豁免详细设计门禁材料。

### 验收范围完整性判断

当前 AC-001 到 AC-013 已覆盖原始材料中明确提出的首版可观察行为：流程阻断、H5 触发与回填、验证码失败处理、H5 次数上限、宝付侧重发、代理商跳过、进度展示、存量一次性处理、完成态只读、短信内容。

仍然不能说“详细设计验收范围完整”。原因是材料没有提供现有系统边界、接口、字段、状态机和失败恢复合同。因此，当前验收范围完整性的结论是：

- **需求验收范围：基本完整，已覆盖材料中的显性功能与规则。**
- **详细设计验收范围：不完整，必须等三项详细设计门禁材料补齐或豁免。**

前版缺口：短信内容没有独立验收项。已补为 AC-013。

### 领域判断

本需求主域判断为 `risk_compliance`，关联 `merchant_platform_relationship`。

判断依据：

- 原始目标是“保证业务合规”和“确认开立特约商户真实意愿”。
- 核心事实是法人认证、授权/同意记录、合规核查证据。
- 流程落点在商户开通、产品能力开通进度和 118 / 83 之前的准入阻断。

排除判断：

- 不把 `account_balance` 作为主域。材料提到电子户，是投诉背景和风险来源，不是要求设计账户余额、账务、电子户生命周期或银行开户模型。
- 不把 `embedded_financial_products` 作为主域。材料没有要求设计银行电子户产品能力，只要求在多渠道收款开通前增加法人短信认证。
- 不把 `payment_transaction` 作为主域。材料没有涉及支付订单、扣款、退款、交易状态。

因此，当前领域复核结论是：**风险合规主域成立，商户开通关系为支撑域；账户/电子户领域只作为背景，不进入首版需求验收。**

## 背景

近期出现业务风险投诉：部分开通银行电子户的多渠道收款商户法人反馈对电子户开通不知情，银行要求我方核查。为保证业务合规，存量和后续新增的多渠道收款商户需要增加法人真实意愿核验。

这里的“电子户”是风险背景，不是本需求的主设计对象。本次主线是法人短信认证、开通流程阻断、验证完成后继续、后台重发、进度可见和跳过规则。

## 首版范围

首版业务范围限定为多渠道收款业务，且业务属性为：

- 抖音平台-商品购销
- 本地生活-商品购销
- 掌财狸

首版新增链路：

- 新会员 BM/API 入口：提交 118 流程前触发法人短验。
- 老前置入口：机审完成后、发起 83 流程前触发法人短验。

存量链路：

- 存量商户是一次性事项。
- 不新增存量短验进度功能。
- 研发按合规提供的商户列表配合发送短信，并配合查看短验进展。

## 流程理解

新增商户通过新会员或老前置开通多渠道收款产品时，如果命中首版范围且未命中跳过规则，系统进入等待法人短验阶段，并向法人发送短验通知短信。法人点击链接进入 H5 后，手动触发验证码短信，回填验证码。验证码正确后，系统记录短验成功，页面展示已完成法人信息核验，原产品开通流程继续。

如果法人不填写验证码，流程持续停留在等待法人短验阶段。等待法人短验是开户流程的一环，不设置过期。只有短信验证码会过期。

如果验证码错误或超时，H5 提示重新触发。若 H5 触发超过 3 次仍未验证成功，页面提示联系宝付重新发送短信，H5 不再允许继续重发。

## 关键规则

| 规则项 | 当前口径 |
| --- | --- |
| 等待法人短验 | 开户流程阶段，不设过期。 |
| 验证码有效期 | 验证码短信 5 分钟内有效。 |
| H5 触发次数 | 超过 3 次仍未成功后，提示联系宝付重发。 |
| 宝付侧重发 | 等待验证状态的商户可在宝付 AD / OMS 重发短验通知短信。 |
| 重发效果 | 重发含链接的短验通知短信，并重置验证码次数。具体重置哪些计数仍需设计确认。 |
| 代理商本身 | 代理商本身开通产品无需法人短验。 |
| 代理商拓展代客 | 按 Apollo 配置，一代直接拓展代客及其二代拓展代客可跳过。 |
| 直客 | 必须进行法人短验。 |
| 存量商户 | 一次性处理，不新增存量进度功能，研发配合查看。 |

## 功能点拆解

### 新会员链路

通过新会员 BM/API 入口开通多渠道收款业务时，在提交 118 流程前触发法人短验。法人验证成功前，产品开通流程不继续提交 118。产品开通进度需要展示“等待法人短验”阶段。

### 老前置链路

通过老前置进件时，在前置进件机审完成后、发起 83 流程前触发法人短验。法人验证成功前，流程不继续发起 83。融证通 OMS 同城机构管理需要展示“是否法人短验”，枚举为“已短验、未短验、无需短验”。

### H5 回填链路

法人从通知短信进入 H5。未验证时，页面提供验证码触发按钮和验证码回填文本框。验证成功后，页面只展示已完成法人信息核验，不允许再次填写或触发短信。

### 宝付侧重发

新会员路径在宝付 AD 的会员产品开通进度操作中增加“法人短验重发”。老前置路径在融证通 OMS 同城机构管理中增加“法人短验重发”。两处都只针对等待验证状态商户。

### 存量一次性处理

合规提供需要处理的存量商户列表。研发按列表批量发送短验通知短信，并配合查看进展。本需求不新增存量进度查询功能。

- 不新增存量商户短验进度查询功能。

- 不把“等待法人短验”做成会过期的任务；等待阶段无过期，验证码才有过期。

- 需求主域是风险合规，关联商户开通和产品能力进度。

## 评审口径

人工评审时建议按下面顺序确认：

1. 首版范围是否只包含三类业务属性。
2. 新会员和老前置的阻断点是否准确。
3. 代理商跳过规则是否覆盖一代、二代和代理商本身。
4. 直客必验是否无例外。
5. 存量是否保持一次性处理且不新增功能。
6. 验证码和等待阶段的过期口径是否无歧义。
7. AD / OMS / H5 / 进度展示是否足够支持运营处理。
